# 가공 에이전트 설계

> 담당: 조영진 · 상태: 초안
> 입출력의 정본은 [인터페이스 정의서](../interface-spec.md) — 여기에는 요약과 링크만 두고, 상세 스키마를 재정의하지 않는다.

## 1. 역할

수집(collect)이 만든 표준 거래 표를 받아, 결제처의 PG사 표기를 실제 가맹점명으로 정규화하고 카테고리를 채운다. 결과는 가맹점·카테고리가 붙은 거래 표(CSV)로, 검증 1·2 단계로 넘어간다.

## 2. 입출력 요약

- 받는 것: 표준 거래 내역 표 (수집 산출물, CSV) — 상세는 [인터페이스 정의서](../interface-spec.md) "가공" 행 / "거래 표 스키마"
- 내놓는 것: 가맹점·카테고리가 붙은 거래 표 — `refine/result.csv`. **CSV**, 거래 표 스키마는 동일하게 유지하고 `결제처`를 정규화하고 `카테고리`를 채운 모양 (분류 체계는 [categories.md](../categories.md)를 따른다)

## 3. 내부 처리 절차

1. 수집 산출물 거래 표(CSV)를 읽는다 (거래 표 스키마 기준)
2. `결제처` 컬럼의 PG사 표기 뒤에 있는 실제 가맹점이 어디인지 판단해 가맹점명으로 정규화한다
3. `결제처`(정규화된 가맹점명)·`구매항목`(영수증에서 추출한 구매 물품)·`비고`(부가 정보) 세 값을 함께 근거로 [categories.md](../categories.md) 체계의 `카테고리`를 채운다. `구매항목`이 비어 있으면(영수증이 없거나 확인 전) `결제처`·`비고`만으로 판단한다
4. 가맹점 식별 또는 카테고리 분류가 불가한 건은 임의로 끼워 맞추지 않고 `확인 필요`로 표시하고 버리지 않는다
5. 거래 표 스키마를 그대로 유지한 채 CSV로 내놓는다 (컬럼 추가·삭제 없이 `결제처`·`카테고리`만 채운다)

## 4. 판단 규칙

(인터페이스 정의서 "단계별 판단할 것"의 가공 단계를 구체화)

- 판단할 것:
  - PG사 이름 뒤의 실제 가맹점이 어디인지 (결제처 정규화)
  - 그 거래가 [categories.md](../categories.md) 체계의 어느 카테고리인지 (분류)
- 판단 기준: 카테고리 분류는 `결제처`·`구매항목`·`비고` 세 값을 함께 근거로 삼는다 + [categories.md](../categories.md) 카테고리 체계
- 애매할 때 참조: `구매항목`·`비고`의 부가 정보, 카테고리 체계 ([categories.md](../categories.md))
- 핵심 지시 (이 에이전트에게 시키는 말의 요지): "PG사 표기 뒤의 실제 가맹점과 카테고리를 근거를 두고 판단하라. 카테고리는 `결제처`·`구매항목`·`비고`를 함께 보고 정한다. 가맹점 식별·분류가 불가하면 임의 배정하지 말고 `확인 필요`로 남기고, 거래 표 스키마는 바꾸지 말고 `결제처`·`카테고리`만 채워라"
- AI 판단이 필요한 곳 / 일반 코드로 처리할 곳:
  - 일반 코드 — 거래 표(CSV) 읽기/쓰기, 스키마 유지, 이미 알려진 PG사→가맹점 매핑 규칙 적용
  - AI 판단 — PG사 표기 뒤 실제 가맹점 추론, `결제처`·`구매항목`·`비고` 기반 카테고리 분류

## 5. 오류·예외 처리

- 가맹점 식별 불가·카테고리 분류 불가 건은 `확인 필요`로 표시하고 버리지 않는다 (인터페이스 정의서 가공 "못 할 때", [categories.md](../categories.md) 운영 규칙)
- 입력 거래 표가 비어 있으면 처리 대상 없음으로 보고한다 (단계 결과 보고 `status`=`empty`)
- 실패를 조용히 삼키지 않는다 (공통 규칙 AGENTS_COM.md §4)

## 6. 사용 도구·의존성

- 언어: Python (프로젝트 공통 — 버전·패키지 매니저 미정). 단, refine 에이전트는 `Read`/`Write`만 쓰고 산출물이 CSV(텍스트)라, 별도 엑셀 라이브러리 없이 처리한다 (중간 전달 형식 CSV 통일 — 인터페이스 정의서 "다음 단계" 확정 항목)
- 결제처 정규화·카테고리 분류에 쓸 규칙/모델: 미정 — PG사 매핑 규칙 소스와 AI 분류 방식 확정 필요

## 7. 테스트 방법

수집 산출물 견본(가짜 데이터 기반)을 입력으로 삼아 테스트한다 (실데이터 사용 금지 — AGENTS.md §8).

| 샘플 입력 | 기대 출력 |
|---|---|
| PG사 표기가 붙은 결제처 행 (예: `NHN KCP/실가맹점명`) | `결제처`가 실제 가맹점명으로 정규화된 행 |
| 명확히 분류 가능한 거래 (예: 카페 결제) | `카테고리`가 [categories.md](../categories.md) 체계로 채워진 행 |
| `구매항목`이 있는 거래 (예: 배달의민족 / 부대찌개) | `구매항목`을 근거로 `식비`로 분류 |
| 가맹점 식별·분류가 애매한 거래 (예: PG 표기 + `구매항목` 빈 값) | `확인 필요` 표시, 임의 카테고리 배정하지 않음 |
| 스키마 보존 확인 | 입력 대비 컬럼 추가·삭제 없이 `결제처`·`카테고리`만 갱신 |

견본 파일(`refine/input-sample.md`·`refine/stub.md`)은 이 가짜 데이터 기준으로 만든다.

## 8. 막힌 점

- **카테고리 체계 미확정** — [categories.md](../categories.md)가 아직 "제안" 상태(팀 검토 후 확정)라, 분류 기준이 바뀌면 이 단계도 함께 갱신해야 한다
- **PG사→실가맹점 매핑 소스 미정** — 정규화의 근거가 될 매핑 규칙/데이터 출처가 확정되지 않았다
- **칸 폴더 견본 정합 필요** — `refine/`에 `README.md`·`input-sample.md`는 만들었으나, 팀이 (1) 중간 산출물 형식을 CSV로, (2) 분류 보조 컬럼을 `구매항목`(collect 산출물 맨 끝 컬럼)으로 확정(2026-08-12)했다. 그래서 `input-sample.md`는 새 [collect/result.csv](../../collect/result.csv)(`구매항목` 포함) 기준으로 다시 만들어야 하고, `stub.md`(산출물 모양 견본)는 CSV·`구매항목` 기준으로 작성 예정이다
- (해소됨) ~~구매 품목 입력 계약~~ — 카테고리 분류 보조에 쓸 `구매항목` 컬럼은 팀이 거래 표 스키마에 확정 추가했고 수집(collect)이 채운다. 영수증이 없거나 확인 전이면 빈칸일 수 있어, 빈칸이면 `결제처`·`비고`만으로 판단한다
