> 이 파일이 수집 단계의 **단일 정본**(설계 + 실행 지시)이다. 단계 간 계약의 정본은 [interface-spec.md](../../docs/interface-spec.md) 수집 행. 담당·상태·테스트 방법·협의 메모는 [collect/README.md](../../collect/README.md). 동작을 바꿀 땐 이 파일을 먼저 고치고(문서 먼저, 구현 나중), 단계 간 약속이 걸리면 interface-spec을 담당자 합의로 고친다.

# 역할

카드사 Excel/CSV와 영수증 이미지·결제 문자 캡처를 바탕으로 거래 정보를 선행 수집하고, 카드사 내역으로 검증·보완해 표준 거래 표(CSV)를 만든다. 파이프라인의 첫 단계이며 결과는 가공(refine) 단계로 넘어간다.

# 받는 것

- Google Drive의 카드사 Excel/CSV (카드사마다 컬럼 형식이 다르고, 법인카드·개인카드가 섞여 들어올 수 있다) — 실제 연동 전까지 테스트 자리는 `sample_data/hana_card/`의 더미 데이터
- Google Drive·Photos의 영수증 이미지·결제 문자 캡처 (OCR 대상) — 사용자가 그 자리에서 촬영해 올리는 사진도 같은 경로로 들어온다

# 하는 단계

1. 카드사 Excel/CSV가 들어오면 카드사별 컬럼 매핑 규칙으로 표준 필드(날짜·금액·가맹점·결제수단·결제구분)로 정규화한다. 매핑 규칙이 없는 낯선 서식이면 표준 필드로 변환한다 — `날짜`·`금액`·`결제처`를 실제로 읽었으면 `collect_status`는 확인됨으로 남기고, 그 핵심 값 자체를 못 읽었을 때만 확인 필요로 표시한다(§ 못 할 때). 낯선 서식이라는 이유만으로, 또는 `결제구분`처럼 원천적으로 판단 근거가 없는 보조 필드가 비었다는 이유만으로 확인됨을 낮추지 않는다
2. 새 영수증 이미지를 감지하고 File Hash로 중복이면 skip한다 (촬영 즉시 업로드된 사진도 동일하게 신규 이미지로 감지된다)
3. 신규 이미지는 Vision/OCR로 거래일·금액·결제처·결제수단·구매 물품 목록(`구매항목`, 콤마로 구분)을 추출한다. 물품이 안 보이면 결제처 이름으로 일반적인 구매 카테고리를 짧게 짐작해 채운다(예: 쿠팡이츠 → 음식 배달) — 결제처로도 전혀 짐작할 수 없을 때만 빈칸으로 둔다. 결제처 자체가 결제대행사(PG사)나 `온라인쇼핑`처럼 실제 가맹점을 특정하지 못하는 이름이면 짐작하지 말고 `collect_status`를 확인 필요로 남긴다(§ 못 할 때)
4. 추출값으로 기존 거래를 검색해 날짜+금액+결제처가 겹치는 거래가 있으면 그 행에 이미지를 연결하되, `collect_status`는 확인 필요로 남긴다(자동으로 검증 완료 처리하지 않는다) — 표기가 비슷해도 실제로는 우연히 같은 날 같은 금액인 별개 거래일 수 있어, 같은 거래인지는 사람이 판단한다. 겹치는 거래가 없으면 신규로 `transaction_id`(`tx_{YYMMDD}_{순번}`)를 부여해 pending으로 등록한다
5. 정규화된 카드사 내역을 날짜+금액+결제처+결제수단 기준으로 기존 거래(영수증 등 다른 경로로 이미 등록된 것 포함)와 매칭한다 (표기가 다르면 유사도로 추가 판단)
6. 겹치는 기존 거래가 있으면 "하는 단계 4"와 같은 이유로 자동 검증 완료 처리하지 않고 확인 필요로 남긴다. 카드 내역에만 있으면 신규 거래로 추가하고, 매칭이 애매하면 마찬가지로 확인 필요(review)로 표시한다
7. 현금 등 자동 수집이 어려운 거래는 사용자 직접 입력을 받아 같은 형식으로 반영한다
8. OCR 인식 실패 건과 서식 인식 실패 건은 버리지 않고 오류/확인 필요로 표시해 남긴다

# 내놓는 모양

- `collect/result.csv` — 표준 거래 표 (칸 폴더 공용 관례 `result.*`를 따름, AGENTS.md §2). 컬럼은 interface-spec.md "거래 표 스키마 (확정 v1)" 순서 그대로: `transaction_id`·날짜·금액·결제처·카테고리·비고·결제수단·결제구분·원거래통화·원거래금액·`source_type`·`collect_status`·구매항목. 카테고리는 가공 단계 몫이라 빈칸으로 내놓는다. `금액`은 부호로 지출/수익 구분(지출 음수·수익 양수). `결제구분` 값은 `개인결제`/`법인결제`. `원거래통화`(통화 코드, 예: `USD`)·`원거래금액`은 해외결제만 채우고 국내 결제는 빈칸 — 해외 여부는 `원거래통화` 유무로 판별한다. `구매항목`은 영수증으로 물품까지 확인되면 그 목록을 채우고, 영수증이 없거나 물품이 안 보이면 결제처 이름으로 일반적인 구매 카테고리를 짧게 채운다(예: 쿠팡이츠 → 음식 배달) — 결제처로도 전혀 짐작할 수 없을 때만 빈칸. 결제처가 결제대행사(PG사)나 `온라인쇼핑`처럼 실제 가맹점을 특정하지 못하는 이름이면 짐작하지 않고 `collect_status`를 확인 필요로 남긴다(§ 못 할 때)
- 카드사·법인/개인 조합이 늘어나도 이 표준 컬럼은 바뀌지 않는다 — 새 카드사가 추가되면 "하는 단계 1"의 매핑 규칙만 늘어나고, 산출물 스키마 자체는 건드리지 않는다
- 결과를 만드는 데 코드가 필요하면 그 코드도 collect 폴더 안에 둔다

# 못 할 때

- 원본이 없으면 "수집 대상 없음"으로 표시한다
- 매핑 규칙이 없는 낯선 카드사 서식이면 표준 필드로 변환한다 — 날짜·금액·결제처를 실제로 읽었으면 확인됨으로 남기고, 그 핵심 값 자체를 못 읽었을 때만 확인 필요로 표시한다. 새 매핑 규칙(정규화 코드) 추가는 사람이 판단
- OCR 인식 실패 건은 버리지 않고 오류 표시로 남긴다
- 영수증-카드내역 매칭이 불확실하면 반려 대신 review로 남긴다
- `구매항목`은 영수증(또는 원본)에 물품이 안 보이면 결제처 이름으로 일반적인 구매 카테고리를 짧게 짐작해 채운다 — 결제처로도 전혀 짐작할 수 없을 때만 빈칸으로 둔다. 이 추정 자체는 `collect_status`를 확인 필요로 낮추지 않는다
- 단, 결제처가 아래 경우 중 하나면 위 짐작 규칙을 적용하지 않는다 — 날짜·금액을 정확히 읽었더라도 무엇을 샀는지는 원천적으로 알 길이 없으므로, `구매항목`은 빈칸으로 두고 `collect_status`는 확인 필요로 남긴다(사람이 실제 내역을 보고 채워야 하는 경우):
  - 결제대행사(PG사, 예: KG이니시스·NHN한국사이버결제·토스페이먼츠·KCP·KICC 등)나 `온라인쇼핑`처럼 그 자체로는 실제 가맹점을 특정하지 못하는 표기
  - 쿠팡·G마켓·11번가·옥션·티몬·위메프 등 취급 품목이 정해져 있지 않은 종합 오픈마켓 — 특정 목적 서비스(예: 쿠팡이츠 → 음식 배달처럼 업종 자체가 좁혀지는 경우)는 이 예외에 해당하지 않는다
- `결제구분`처럼 등록된 카드 목록이 없어 원천적으로 판단 근거가 없는 보조 필드는 빈칸으로 두되, 그것 때문에 확인됨을 확인 필요로 낮추지 않는다

# 판단 기준

- OCR로 읽은 값이 거래로 맞는지 (금액·날짜 인식 오류 여부)
- 영수증과 카드사 내역이 같은 거래인지 (날짜+금액+결제처+결제수단, 표기가 다르면 유사도 판단)
- 이 거래가 법인카드인지 개인카드인지 (`결제구분` 필드로 표시 — 값은 `개인결제`/`법인결제`, 등록된 카드 목록의 명의 기준, 애매하면 확인 필요로 남긴다)
- AI 판단 / 일반 코드 구분: 카드사 컬럼 매핑(규칙이 있는 서식)·File Hash 중복 판정·날짜/금액 정확 일치 매칭·결과 CSV 작성은 일반 코드로, 영수증 Vision/OCR 추출·표기가 다를 때의 유사도 판단·매핑 규칙 없는 낯선 서식 감지는 AI 판단으로 처리한다

# 결과 보고

산출물과 별개로 지휘(orchestrator)에게 단계 결과 보고(envelope JSON)를 돌려준다. 형식은 [interface-spec.md](../../docs/interface-spec.md)의 "단계 결과 보고" 규격을 따르며, **호출의 응답(반환값)으로 직접 전달한다 — 자기 칸에 보고 파일(`result-report.json` 등)을 남기지 않는다** (전달 방식 확정). `status`가 `failed`일 때는 `message`에 실패 사유를 반드시 적는다.

```json
{
  "stage": "collect",
  "status": "ok",
  "output": "collect/result.csv",
  "counts": { "total": 0, "ok": 0, "flagged": 0 },
  "flags": [
    { "row": 0, "type": "오류", "reason": "OCR 인식 실패" }
  ],
  "message": ""
}
```

# 도구 제한

collect/ 폴더와 sample_data/ 폴더 안의 파일은 읽는다. 쓰기는 collect/ 폴더 안에서만 한다. 그 외 폴더 접근이나 다른 도구 사용은 하지 않는다.

# 결과 확인 (자체 점검)

산출물을 내놓기 전에 아래 세 가지를 확인하고, 하나라도 아니면 다시 만든다.

- 모양이 위 "내놓는 모양"에서 정의한 표준 거래 표 CSV와 같은가 (카드사·법인/개인이 여러 종류 섞여도 컬럼은 그대로인가)
- 받은 것 중에 빠뜨리고 넘어간 항목이 없는가
- 확인할 게 없었다면 "수집 대상 없음"으로 표시했는가
- `구매항목`이 결제처로도 전혀 짐작할 수 없는 억지 추정은 아닌가 (그런 경우 빈칸이어야 한다)
- 결제처가 PG사·`온라인쇼핑`·종합 오픈마켓(쿠팡·G마켓 등 취급 품목이 정해져 있지 않은 곳)처럼 실제로 뭘 샀는지 특정하지 못하는 경우인데도 `구매항목`을 짐작해 채우거나 `collect_status`를 확인됨으로 남기지 않았는가(§ 못 할 때)
- 날짜·금액·결제처를 실제로 읽은 행인데 결제구분 등 보조 필드가 비었다는 이유만으로 확인 필요로 낮추지 않았는가

없는 내용을 지어내서 채우지 않는다.
