# 온보딩 가이드 — 처음 오신 분을 위한 안내

> 이 프로젝트가 뭔지, 나는 어디서 뭘 하면 되는지를 잡는 게 목표인 문서입니다.

## 1. 이 프로젝트는 뭘 만드나요

여러 장의 카드(개인·법인) 결제 내역을 모아서 **월 결산 산출물(엑셀 회계장부 + PDF 리포트)을 자동으로 만드는 AI 시스템**, "월말결산 에이전트"입니다.

공장 조립 라인을 떠올리면 됩니다. 재료가 라인을 타고 흐르면서 단계마다 담당 기계(=AI 에이전트)가 한 가지 일을 합니다:

| 순서 | 단계 | 하는 일 | 담당 |
| --- | --- | --- | --- |
| 1 | 수집 (collect) | 카드사 엑셀·영수증 사진을 모아 거래 표로 | 이승환 |
| 2 | 가공 (refine) | 결제처를 알아보기 좋게 정리하고 카테고리 분류 | 조영진 |
| 3-a | 검증 1 (verify1) | 분류가 기준에 맞는지 확인 (3-b와 동시에) | 김윤덕 |
| 3-b | 검증 2 (verify2) | 날짜·금액이 기준에 맞는지 확인 (3-a와 동시에) | 이지은 |
| 3-c | 검증 3 (verify3) | 법인카드 부정 사용 점검 — 부정 사용 감지 토글을 켠 실행만 (3-a·3-b와 동시에) | 김규은 |
| 4 | 통합 (merge) | 통과한 것들로 장부·리포트 완성 | 박인혜 |
| — | 지휘 (orchestrator) | 위 단계들을 순서대로 부르고 마무리 | 김규은 |

여러분이 만드는 건 **이 중 자기 단계 하나**입니다. 전체를 다 알 필요 없이, 내 단계가 "무엇을 받아서 무엇을 내놓는지"만 지키면 전체가 맞물려 돌아갑니다.

## 2. 뭘 보고 시작하나요 (폴더 지도)

| 위치 | 뭐가 있나 | 언제 보나 |
| --- | --- | --- |
| `README.md` | 전체 소개와 문서 링크 | 맨 처음 |
| `docs/PRD.md` | 뭘 왜 만드는지, 역할 분담 | 처음 한 번 |
| `docs/interface-spec.md` | ⭐ **단계끼리 주고받는 약속** — 내 단계의 입력·출력·형식·문제 시 처리 | 개발 내내 |
| `docs/categories.md` | 카테고리 분류 기준 (가공·검증 1이 주로 사용) | 해당 담당자 |
| `.claude/agents/<내 단계>.md` | **내 단계 문서 — 설계와 에이전트 실행 지시가 한 파일 (단일 정본, 내가 채우는 문서)** | 내 작업의 시작점 |
| `<내 단계>/` (예: `collect/`) | **내 칸 폴더** — 약속(README)·받는 재료 견본(input-sample)·모양 견본(stub)·진짜 산출물(result)·필요한 코드가 전부 모이는 자리 (검증 담당은 `verify1/`·`verify2/`) | 개발 내내 |
| `sample_data/` | 테스트용 가짜 데이터 (여기만 커밋 가능) | 테스트할 때 |
| `logs/` | 실행 기록 — 커밋 안 됨 | 문제 추적 시 |

> 📖 **작업을 시작하기 전에 위 문서들(README·PRD·인터페이스 정의서·카테고리·내 단계 문서)을 한 번씩 읽어보길 권합니다.** 30분이면 전체 그림이 잡히고, 이후 모든 결정이 빨라집니다.

> ⚠️ **진짜 카드 내역·비밀번호·API 키는 절대 repo에 넣지 않습니다.** 차단 장치(.gitignore)가 있지만, 스스로도 한 번 더 확인하는 습관이 안전합니다.

이 중 헷갈리기 쉬운 두 문서만 짚고 갑니다:

- **인터페이스 정의서** (`docs/interface-spec.md`) — 단계 **사이**의 약속입니다. 콘센트 규격처럼 "누가 무엇을 어떤 모양으로 어디에 두는지"를 정해둔 **모두의 공용 문서**라, 바꾸려면 관련 담당자와 합의해야 합니다. 쓰이는 때: 개발 시작 전 내 줄 확인 → 개발 중 입출력 형식 확인 → 약속을 바꾸고 싶을 때 합의의 기준.
- **단계 문서** (`.claude/agents/<내 단계>.md`) — 내 단계 **안**의 설계도이자 에이전트에게 시키는 말입니다. 내 기계가 어떤 절차로 돌고 무엇을 기준으로 판단하는지를 적는 **내가 채우는 내 문서**이고, 이 파일이 그대로 에이전트의 지시문이 되므로 고치면 동작에 바로 반영됩니다. 담당·상태·테스트 방법·협의 메모 같은 사람용 내용은 여기 넣지 않고 **내 칸 폴더의 `README.md`** 에 적습니다 (단계 문서는 통째로 에이전트에게 주입되기 때문).

한 줄 요약: **인터페이스 = 단계 밖(모두의 약속), 단계 문서 = 단계 안(내 계획 + 실행 지시), 칸 README = 사람용 메모.**

## 3. 처음 한 번만 — 초기 세팅

두 가지만 하면 됩니다:

1. **프로젝트 내려받기 (clone)** — 프로젝트를 두고 싶은 폴더에서 클로드를 열고 이렇게 말합니다:
	> "https://github.com/team-T6/ledger-flow 저장소를 clone해줘"

	끝나면 VSCode에서 `ledger-flow` 폴더를 열고, 거기서 Claude를 엽니다. 이제 여기서 작업을 시작합니다.
2. **git 이름 설정** — `ledger-flow` 폴더에서 클로드에게 이렇게 말하면 끝:
	> "이 저장소의 git user.name을 **honggilDong**으로 설정해줘" (본인 이름을 영어로 — 형식은 자유, 브랜치 이름은 클로드가 규칙에 맞게 다듬어 만듭니다)

	이 이름이 앞으로 내 작업 브랜치 이름(`feature/honggil-dong`)이 됩니다

여기까지 하면 준비 끝 — 이후로는 아래의 작업 흐름만 돌면 됩니다.

## 4. 어디부터 시작하나요

1. `README.md` → `docs/PRD.md`를 한 번 읽고, `docs/interface-spec.md`에서 **내 단계 줄**을 찾아 읽습니다 (받는 것 / 내놓는 것 / 모양 / 못 할 때)
2. 지금 문서들은 초안이라 곳곳에 **미정** 표시가 있습니다. 내 단계에 걸린 미정을 확정하는 게 첫 작업입니다 — 지금 설계는 임의 초안이므로, 내 단계의 판단 기준·입출력이 이상하면 바꾸시면 됩니다
3. `.claude/agents/<내 단계>.md`(내 단계 문서)를 채웁니다 — 역할, 처리 절차, 판단 규칙, 그리고 **블로커**(에이전트가 임의로 채우면 안 되는 것). 최대한 구체적으로 작성합니다. 이 파일이 그대로 에이전트의 지시문이 됩니다. 혼자 못 정하는 협의 사항·테스트 방법은 내 칸 폴더 `README.md`에 적습니다
4. 잘 모르겠거나 의견이 필요하면 혼자 정하지 말고 팀 채팅에서 다 같이 의견을 구합니다. 단체방을 적극 활용해주세요!

## 5. 뭘 만들면 되나요

내 에이전트가 최종적으로 내놓는 건 **두 가지**입니다:

1. **실제 산출물** — 내 단계의 "내놓는 것" (예: 가공이면 카테고리 붙은 거래 표). 내 칸 폴더(`<내 단계>/`)에 `result.*`로 생성 — 모양 견본 `stub.md` 옆에 만든다. 실데이터로 실행한 결과는 커밋하지 않는다
2. **결과 보고** — 지휘에게 보내는 요약 JSON (몇 건 처리했고 문제가 뭔지). 형식은 interface-spec의 "단계 결과 보고" 참고

순서는 **문서 먼저, 구현 나중**입니다: 단계 문서와 인터페이스를 확정한 뒤에 만들기 시작합니다. 그리고 인터페이스는 혼자 소유하는 게 아니라서 —

- **내 앞 단계**가 내놓는 것(=내가 받는 것)의 명세를 읽고, 이상하면 피드백합니다
- **내 뒤 단계**에게는 "내 출력을 이렇게 줘도 되는지" 물어봅니다
- 약속을 바꾸게 되면 interface-spec 문서를 먼저 고치고 관련 담당자와 합의합니다

내 앞·뒤 단계가 누구인지는 아래 표로 확인하세요 — 검증이 병렬(2명)이라 **앞뒤가 한 명이 아닌 단계**가 있습니다:

| 내 단계 | 내가 받는 것을 만드는 사람 (형식이 불편하면 이쪽에 피드백) | 내 출력을 받는 사람 (바꾸기 전에 이쪽에 미리 확인) |
| --- | --- | --- |
| 수집 | (원천 파일 — 없음) | 가공 |
| 가공 | 수집 | **검증 1·2 둘 다** |
| 검증 1 | 가공 | 통합 |
| 검증 2 | 가공 | 통합 |
| 통합 | **가공 + 검증 1·2 셋 다** (거래 표와 두 검증 결과를 받아 합치므로) | (최종 — 없음) |

**에이전트를 고치고 싶을 때도 같은 순서입니다** — 실행 코드를 바로 고치는 게 아니라, **관련 문서를 먼저 고칩니다**:

1. 무엇이 바뀌는지에 따라 고칠 문서가 다릅니다:
	- 내 단계 **안**의 동작(처리 절차·판단 규칙·핵심 지시)이 바뀌면 → `.claude/agents/<내 단계>.md` — 이 파일이 곧 에이전트 지시문이라 고치면 동작에 바로 반영됩니다
	- 단계 **사이** 약속(입출력·형식·결과 보고)이 바뀌면 → `docs/interface-spec.md` (관련 담당자와 합의 필수)
	- **분류 기준**이 바뀌면 → `docs/categories.md`
2. 별도 실행 코드(파이썬 스크립트 등)가 있는 단계는, 문서를 고친 뒤 클로드에게 "문서 바뀐 대로 코드에 반영해줘"라고 시킵니다

문서를 건너뛰고 코드만 고치면 문서와 실제 동작이 어긋나서, 다음에 보는 사람(그리고 클로드)이 문서를 믿을 수 없게 됩니다.

## 6. 작업한 걸 어떻게 올리나요 (커밋과 PR)

먼저 개념 4개만 알고 가면 됩니다 (30초):

- **커밋(commit)** — 지금까지의 작업을 저장하는 것. 게임의 세이브 포인트처럼 언제든 이 시점으로 돌아올 수 있습니다. 아직 **내 컴퓨터에만** 저장된 상태입니다
- **푸시(push)** — 그 저장본을 **모두가 보는 공유 저장소(GitHub)에 올리는 것.** 올려야 팀원들도 볼 수 있습니다
- **브랜치(branch)** — 작업 줄기. 우리는 각자 자기 줄기(`feature/내이름`)에서 작업합니다. **내 브랜치에서는 커밋하고 push해도 메인 줄기(main)와 별개로 저장되니, 뭔가 망가뜨릴까 걱정하지 않아도 됩니다**
- **PR(Pull Request)** — "내 브랜치에서 작업한 걸 main에 반영해 주세요"라는 요청. 리뷰어가 확인한 뒤에 main에 합쳐집니다

그리고 git 명령어는 몰라도 됩니다 — **클로드에게 시키면 됩니다.** 흐름은:

1. 작업 끝나면 클로드에게 **"커밋해줘"** — 그러면 클로드가 알아서 처리합니다: 다른 팀원이 올린 main의 새 변경을 먼저 동기화하고, 이번 변경이 기능 개발이면 자기 브랜치(`feature/내이름`)를 만들어(있으면 이동해) 진행합니다. user.name이 설정 안 돼 있으면 설정해 달라고 요청하니, §3 초기 세팅의 이름 설정을 확인하세요
2. 클로드가 커밋 내용을 제안하고 "이대로 커밋할까요?" 물어봅니다 → 확인하고 승인
3. **"PR 올려줘"** → 클로드가 PR 내용 초안을 써서 보여줍니다 → 확인·수정하고 승인 (리뷰어 지정도 자동)
4. 기능 개발은 main에 직접 커밋하지 않습니다 — 문서·설정 같은 공통 작업만 main에서 처리되고, 애매하면 클로드가 물어봅니다

## 7. 테스트는 어떻게 하나요

- 테스트는 **항상 `sample_data/`의 가짜 데이터로만** 합니다. 진짜 카드 내역은 금지
- 기본 루프: 내 단계의 입력 샘플 준비 → 실행 → 출력이 interface-spec의 "모양"과 맞는지 확인 → 내 칸 README의 "테스트 방법"에 기록
- 가짜 데이터(카드 엑셀·영수증 등) 만드는 것도 클로드에게 부탁하면 됩니다

- "이 프로젝트 구조 설명해줘. 나는 가공 담당이야"
- "인터페이스 정의서에서 내 단계 부분을 쉽게 설명해줘"
- "내 단계 문서 같이 채워보자"

- "지금 내 단계에 걸린 미정 항목이 뭐야?"
- "커밋해줘" / "PR 올려줘"

클로드로도 안 풀리는 것, 특히 **설계가 바뀌는 결정은 혼자 하지 말고 팀 채팅에** 공유해 주세요.
