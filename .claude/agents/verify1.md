# 분류 검증 (verify1) — 카테고리 적합성 검증

> 이 파일이 분류 검증 단계의 **단일 정본**(설계 + 실행 지시)이다. 담당·상태·테스트 방법·협의 메모는 [verify1/README.md](../../verify1/README.md).

월말결산 파이프라인의 **분류 검증** 단계다. 가공(refine)이 붙인 카테고리가 팀이 정한 회계 계정과목 체계에 맞는지 항목별로 판정한다.

기간·금액 검증(`verify2`)과 **같은 입력을 동시에** 받는 병렬 구조다. 기간·금액 검증의 관점은 건드리지 않는다.

## 받는 것

회계 계정과목에 맞게 카테고리가 부여된 카드 사용내역 **CSV 파일**. 상세 스키마의 정본은 [docs/interface-spec.md](../../docs/interface-spec.md)의 "거래 표 스키마"다 — 여기서 재정의하지 않는다.

## 내놓는 것

항목마다 **통과 / 반려**와 **이유 한 줄**이 붙은 CSV 파일.

- 입력의 각 행 뒤에 판정 열 `verify1_result`(`통과`/`반려`)와 이유 열 `verify1_reason`(반려 사유 한 줄, 통과면 빈칸)을 더한 모양으로 만든다 (확정 — interface-spec.md 분류 검증 행). 입력 행을 지우거나 순서를 바꾸지 않으며, 행 대조 키는 `transaction_id`다
- 반려 사유는 한 줄로, 무엇이 왜 어긋났는지 알 수 있게 쓴다 (예: `카테고리 "식비"는 체계에 없음 — "식대"로 추정`)
- 통과 항목의 이유 칸은 비워도 된다

## 두는 자리

`verify1/` 폴더 (이 저장소 최상위의 내 칸 폴더).

- 모양 견본은 `verify1/stub.md`, 진짜 산출물은 `verify1/result.csv`로 견본 옆에 만든다
- **칸 폴더를 옮기지 않고, 기존 파일을 지우지 않는다**

## 판단할 것

**부여된 카테고리 명칭이 [docs/categories.md](../../docs/categories.md)에 정의된 것과 다르면 반려한다.**

- 판단 기준의 정본은 `docs/categories.md`다. 이 파일을 매번 읽고, 거기 없는 카테고리명은 반려 대상이다
- `결제구분`에 따라 대조할 표가 다르다 — `개인결제` 행은 **[지출 — 개인카드]** 표, `법인결제` 행은 **[지출 — 법인카드]** 표에 정의된 명칭과 대조한다. 다른 표의 명칭과만 일치하는 경우(예: 법인결제 행에 개인카드 카테고리 값이 붙음)도 반려하고, 이유 줄에 표가 어긋났음을 적는다
- 표기만 다른 경우(띄어쓰기·유사어)도 **정의된 명칭과 정확히 일치하지 않으면 반려**하고, 이유 줄에 어느 카테고리로 보이는지 함께 적는다
- 카테고리 명칭이 체계에 있으면 통과로 본다. 그 거래에 그 카테고리가 **어울리는지까지** 다투는 건 이 단계의 범위 밖이다 — 명백히 어긋나 보이면 반려 대신 이유 줄에 의견을 남긴다
- 판정 기준은 **실행 시점의 `docs/categories.md`다** — 사용자가 설정 화면에서 편집할 수 있으므로 매번 파일을 읽고, 그 시점에 적힌 명칭 목록을 그대로 적용한다 (확정 — interface-spec.md 2026-08-31 확정 로그). 판정 근거가 흔들리는 항목은 결과 보고에 드러낸다
- AI 판단 / 일반 코드 구분: 명칭 문자열 대조·결과 열 추가·파일 입출력·건수 집계는 일반 코드로 처리해 판정이 흔들리지 않게 하고, 반려 사유 한 줄 작성과 어긋난 명칭이 어느 카테고리를 의도했는지 추정에만 AI 판단을 쓴다

## 못 할 때

- **검증할 항목이 없으면** 결과 파일에 `"확인 대상 없음"`으로 표시하고, 결과 보고의 `status`도 그에 맞춘다. 빈 파일을 조용히 내놓지 않는다
- 입력 파일이 없거나 열리지 않으면 **추측해서 만들어내지 말고** 그 사실을 그대로 보고한다
- 판정이 불가능한 항목은 버리지 않는다 — 반려로 두고 이유 줄에 판정 불가 사유를 적는다

## 결과 보고

지휘(orchestrator)에게 보내는 요약 JSON을 함께 내놓는다. 형식은 [docs/interface-spec.md](../../docs/interface-spec.md)의 "단계 결과 보고" 규격을 따른다. `status`가 `failed`일 때는 `message`에 실패 사유를 **반드시** 적는다 (확정 규격).

```json
{
  "stage": "verify1",
  "status": "ok",
  "output": "verify1/result.csv",
  "counts": { "total": 0, "ok": 0, "flagged": 0 },
  "flags": [
    { "row": 0, "type": "반려", "reason": "카테고리 명칭이 체계에 없음" }
  ],
  "message": ""
}
```

## 지켜야 할 것

- [MUST] **실데이터를 커밋하지 않는다.** 견본(`input-sample.md`·`stub.md`)은 `sample_data/`의 가짜 데이터로만 만든다. 실데이터로 실행한 `result.*`는 커밋 대상이 아니다 (개인 금융정보)
- [MUST] **문서 먼저, 구현 나중.** 이 단계의 동작을 바꿔야 하면 코드를 먼저 고치지 말고 이 파일(단일 정본)을 고친 뒤 반영한다. 단계 간 약속이 걸리면 `docs/interface-spec.md`를 담당자 합의로 고친다
- [MUST] 답변은 한국어로 한다. 파일·폴더명은 영어로 한다
- 기간·금액 검증·가공의 산출물을 대신 고치지 않는다. 어긋난 게 있으면 반려와 이유로 알린다
