# 수집 (collect) — 이 칸의 약속

> 담당: 이승환 · 상태: 초안 (실행하며 검증 중)
> 계약의 정본은 [인터페이스 정의서](../docs/interface-spec.md), 단계 문서(설계+실행 지시의 단일 정본)는 [.claude/agents/collect.md](../.claude/agents/collect.md).

## 하는 일

카드사 Excel/CSV와 영수증 이미지·결제 문자 캡처를 바탕으로 거래 정보를 선행 수집하고, 카드사 내역으로 검증·보완해 표준 거래 표를 만든다. 파이프라인의 첫 단계이며 결과는 가공(refine) 단계로 넘어간다.

## 받는 것 / 내놓는 것

| | 내용 | 모양 |
|---|---|---|
| 받는 것 | 카드사 Excel/CSV (카드사·법인/개인마다 컬럼이 다를 수 있음) + 영수증 이미지·결제 문자 캡처(OCR 대상) + 텍스트 레이어 있는 PDF(카드사 명세서 등). 웹 업로드는 zip으로 묶어 올릴 수 있고, 압축 해제는 수집이 처리 시작 시점에 담당 | 카드사 원본은 CSV/Excel, 이미지는 사진 — [input-sample.md](input-sample.md) |
| 내놓는 것 | 표준 거래 표 | CSV 하나 (`result.csv`) — [stub.md](stub.md) |

카테고리 컬럼은 넣지 않는다 — [categories.md](../docs/categories.md)는 가공(refine) 단계 몫이다. 카드사·법인/개인 조합이 늘어도 표준 컬럼 자체는 바뀌지 않는다.

## 이 칸의 파일

| 파일 | 무엇 |
|---|---|
| `README.md` | 이 문서 — 칸의 약속 |
| `input-sample.md` | 받는 재료 견본 (가짜 데이터) |
| `stub.md` | 산출물 모양 견본 (가짜 데이터) |
| `collect.py` | `sample_data/<YYYY-MM>/`의 하나카드·신한법인카드 CSV를 표준 거래 표로 정규화하는 스크립트 |
| `collect_uploads.py` | 웹 업로드 수집기 — `uploads/inbox/`의 사용자 업로드 파일(카드사 CSV 각종 서식·영수증 이미지·PDF, zip 압축 포함)을 표준 거래 표로 만든다. zip은 먼저 풀어 안의 파일을 개별 원천으로 편입하고, PDF는 텍스트를 뽑아 낯선 서식과 같은 경로로 넘긴다. 정형 서식은 `collect.py` 재사용, 낯선 서식·이미지는 `call-agent.py`의 AI 판단 호출 |
| `call-agent.py` | 수집 담당자(Claude) 호출 유틸 — 텍스트/영수증 이미지 OCR/낯선 서식 표 변환 |
| `server.py` | 연습용 로컬 서버 (포트 8787) — `screen.html`과 호출 유틸을 잇는다 |
| `screen.html` | 연습용 화면 — 데이터 준비 도구 (파이프라인 실행과 무관) |
| `result.csv` | 진짜 산출물 — 실행하면 생김. 지금은 더미 데이터 기반이라 팀 확인 후 예외로 커밋. **실데이터로 실행한 파일은 커밋하지 않는다** |

칸 폴더를 옮기지 않고, 기존 파일을 지우지 않는다. 새 산출물은 견본 옆에 만든다.

## 판단 규칙 (요약)

카드사별 컬럼 매핑으로 표준 필드(날짜·금액·가맹점·결제수단·결제구분)로 정규화하고, 날짜+금액+결제처+결제수단 기준으로 영수증·카드내역을 매칭한다. 상세는 [단계 문서](../.claude/agents/collect.md)에 있다.

- 매핑 규칙이 없는 낯선 카드사 서식이면 임의로 끼워 맞추지 않고 확인 필요로 표시한다
- 영수증-카드내역 매칭이 불확실하면 반려 대신 review로 남긴다
- 법인/개인카드 구분은 `결제구분` 필드(값: `개인결제`/`법인결제`)로 하고, 애매하면 확인 필요로 남긴다 — "본인" 같은 구체적인 명의는 지어내지 않는다
- `구매항목`(가공 담당 요청 — 결제처만으론 카테고리 판단이 어려운 문제 보완)은 영수증으로 확인된 거래(`확인됨`)만 채우고, 확인 전(`확인 필요`)은 빈칸으로 둔다
- 수집할 원본이 없으면 `"수집 대상 없음"`으로 표시한다. 빈 파일을 조용히 내놓지 않는다
- zip 업로드는 압축을 풀어 안의 파일을 개별 원천으로 다룬다. 허용되지 않는 확장자·zip 안의 zip·경로 탈출 항목은 그것만 건너뛰고 오류로 남기며, zip 전체를 버리지 않는다
- PDF는 텍스트 레이어가 있는 문서(카드사 명세서 등)만 지원한다. 텍스트를 못 뽑으면(스캔 이미지 PDF) 오류로 남기고 버리지 않는다

## 지켜야 할 것

- **실데이터를 커밋하지 않는다.** 견본은 [sample_data/](../sample_data/)의 가짜 데이터로만 만든다 (개인 금융정보)
- **문서 먼저, 구현 나중.** 동작을 바꾸려면 [단계 문서](../.claude/agents/collect.md)를 먼저 고친다. 단계 간 약속이 걸리면 [인터페이스 정의서](../docs/interface-spec.md)를 담당자 합의로 고친다

## 테스트 방법

`sample_data/2026-02/`의 더미 하나카드 데이터로 테스트한다 (실데이터 사용 금지 — AGENTS.md §8). 견본 파일(`input-sample.md`·`stub.md`)도 이 가짜 데이터 기준으로 만든다. 더 지저분한 케이스(법인카드 서식·OCR 함정 등)는 `sample_data/2026-06/`~`2026-08/`에 년월 폴더로 있다 ([sample_data/README.md](../sample_data/README.md) 참고).

| 샘플 입력 | 기대 출력 |
|---|---|
| `sample_data/2026-02/2026-02_하나카드_이용내역서.csv` (일시불 거래) | 표준 컬럼으로 정규화된 행, `collect_status`=`확인됨` |
| 6개월 할부 거래(하이마트, 최초 구매 2026-02-10) | 회차마다 같은 `transaction_id`, `날짜`·`금액`만 회차별로 갱신 |
| 영수증 선행 수집 → 이후 카드 내역 매칭 | 매칭 전 `collect_status`=`대기`, 매칭 후 `확인됨`으로 갱신되며 `transaction_id` 유지 |
| 매핑 규칙 없는 낯선 카드사 서식 (날짜·금액·결제처는 읽을 수 있는 경우) | 표준 필드로 변환, `collect_status`=`확인됨` (결제구분 등 보조 필드가 비어도 낮추지 않음) |
| 매핑 규칙 없는 낯선 카드사 서식인데 핵심 값(날짜·금액·결제처)조차 못 읽는 경우 | 확인 필요로 표시, 임의 정규화하지 않음 |
| 영수증으로 구매 물품까지 확인된 거래 | `구매항목`에 물품 목록(콤마 구분) 채움 |
| 영수증이 없거나 물품이 안 보이는 거래 (결제처는 있음) | `구매항목`에 결제처 기반 일반 카테고리 채움 (예: 쿠팡이츠 → 음식 배달), `collect_status`는 낮추지 않음 |
| 결제처로도 구매 카테고리를 전혀 짐작할 수 없는 거래 | `구매항목` 빈칸 |

## 협의 중 / 남은 과제

- **OCR/Vision 도구 미확정** — 영수증·결제 문자 캡처 인식에 쓸 서비스·모델을 팀에서 정해야 한다
- **Google Drive 연동 방식 확정(2026-08-31)** — Claude CLI headless + Drive MCP로 파일을 `uploads/inbox/`에 가져와 기존 웹 업로드 경로로 처리 (수집 동작·스키마 변경 없음 — interface-spec.md 확정 로그). 계정 인증은 시연 머신 사전 1회. **Google Photos 연동은 계속 미정**
- **영수증 이미지 견본 없음** — `input-sample.md`에 카드사 Excel/CSV 예시만 있고, 이미지 원천은 텍스트로 대체할 수 없어 아직 견본이 없다
- **법인카드 더미 데이터 검증 전** — 법인/개인 판별 로직이 실데이터 수준으로 검증되지 않았다
- **`구매항목` 추출 로직 미검증** — 실제 영수증 OCR 연동 시 추출 정확도·물품명 정규화 방식 재검토 필요
