# 월말결산 에이전트 PRD (Product Requirements Document)

> 상태: 초안 (팀 논의용) · 작성 2026-08-05
> 월말결산 에이전트(repo: `ledger-flow`) — 다중 카드 통합 AI 자동 결산 시스템, 멀티 에이전트 파이프라인 팀 프로젝트

## 1. 문제 정의

개인·법인 명의가 섞인 복수의 카드를 운용하는 순간, 지출 데이터는 카드사별 엑셀·영수증 사진·결제 문자로 파편화된다. 월 결산을 하려면 이 이질적인 원천들을 일일이 내려받고, 옮겨 적고, 분류하고, 대조해야 하며 — 이 절차는 매달 같은 순서로 반복되지만 여전히 사람 손으로 돌아가며, 여기에 월 3시간가량이 쓰인다(잠정 — 실측 후 갱신).

문제의 본질은 셋이다.

1. **파편화** — 원천마다 형식이 달라 통합 자체가 수작업이다
2. **반복성** — 동일한 절차가 매달 사람 손으로 재실행된다
3. **불투명성** — 결산이 끝나기 전까지는 지출 현황을 아무도 정확히 모른다

월말결산 에이전트(ledger-flow)는 이 반복 결산을 수집 → 가공 → 검증 → 통합의 멀티 에이전트 파이프라인으로 자동화하고, 사람의 몫은 예외("확인 필요" 건) 처리로 줄인다.

## 2. 목표와 범위

### 1차 산출물 (이번 과정 범위)

**AI 멀티 에이전트 파이프라인**이 카드 결제 원천 데이터를 받아 월 결산 리포트를 자동 생성한다.

- 입력: Google Drive의 카드사 엑셀 + 영수증 사진·결제 문자 캡처(OCR) — 이미지는 Google Drive·Google Photos에서 수집
- 출력: 엑셀로 정리된 회계장부 + PDF 결산 리포트
- 형태: 파이프라인 실행 (수집 → 가공 → 검증 → 통합, 오케스트레이터가 순서 지휘)

### 확장 (시간 여유 시)

- **웹사이트**: 연동(Google 로그인) / 가공 현황(진행 단계·오류 표시) / 리포트 메뉴. 연동·로그인 데이터는 로컬에만 두고 저장하지 않음
	- 데모 운용 (확정): 쇼케이스는 GitHub Pages로 상시 공개(`demo` 브랜치의 `web/` 변경 시 자동 배포), 실제 파이프라인 실행 시연은 로컬 서버 + Cloudflare quick tunnel로 한다 — 절차는 `web/README.md` 참고
- **챗봇**: 결산 데이터 기반 질의응답 — 특정 결제 찾기("이 결제 언제 했지?"), 집계 질문("편의점에서 얼마 썼지?"), 누락 데이터 확인
- **브랜딩 비주얼**: 로고·챗봇 캐릭터 등 비주얼 자산은 이미지 생성 AI로 제작
- **전월 대비 비교**: 여러 달 결산이 쌓인 뒤 리포트에 전월 대비 증감 추가 (1차는 특정 월 단독 결산만)

### 범위 제외 (Non-goals)

- 카드사 API 직접 연동(스크래핑) — 원천은 사용자가 Google Drive·Google Photos에 올린 파일로 한정
- 실시간 처리 — 월 단위 배치 결산이 기본
- 예산 관리·소비 코칭 등 가계부 앱 기능

## 3. 파이프라인 요구사항 (단계별)

| 단계 | 담당 | 역할 | 핵심 요구사항 |
| --- | --- | --- | --- |
| 수집 | 이승환 | 재료를 모아 정리된 모양으로 | Google Drive·Google Photos 연동, 엑셀 파싱, 사진 OCR → 표준 CSV 스키마로 추출 |
| 가공 | 조영진 | 재료를 쓸 수 있는 형태로 | 결제처 정규화 — PG사 결제면 걸러내고 실가맹점명 식별, 카테고리 분류 |
| 검증 1 | 김윤덕 | 기준 적합성 확인 | 카테고리 분류가 정의된 체계에 맞는지 검증 |
| 검증 2 | 이지은 | 기준 적합성 확인 | 대상 월 데이터만 포함됐는지, 해외결제 원화 환산이 맞는지, `금액` 기입이 부호 규칙(지출 음수·수익 양수)에 맞는지 검증 |
| 통합 | 박인혜 | 최종 결과물로 묶기 | 검증 통과 데이터로 월 결산 리포트 생성 (카테고리별 비중 등) |
| 지휘 | 김규은 | 순서대로 부르고 마무리 | 오케스트레이터 — 단계 순차 호출, 실패 처리, 최종 마무리 |

- 각 단계는 독립 에이전트로 구현하고, 단계 간 데이터는 **인터페이스 정의서**(별도 문서)의 계약을 따른다.
- **검증 1·2는 병렬 실행한다** — 직렬 2단계가 아니라 하나의 검증 스테이지 안에 검증기 2개를 두는 구조. 둘 다 같은 가공 결과를 입력으로 받아 각자 검증 리포트를 내고, 통합 전에 두 리포트를 merge한다. (규칙이 서로 독립이라 순서 의존이 없고, 오류를 한 번에 모아 반려 1회로 처리하기 위함)
- 검증 실패·반려 건은 재시도(반려 루프) 없이 통합의 "확인 필요" 목록으로 리포트에 싣는다 — 오류 보고 방식 확정.
- 웹 실행 경로에서는 결산이 끝나기 전 **중간 확인**으로 사용자가 확인 필요·반려 건을 직접 수정·확정할 수 있다 — 수정된 건은 "사용자 확인" 이력과 함께 장부에 반영되고, 그대로 둔 건만 확인 필요 목록에 남는다 (상세는 인터페이스 정의서 확정 로그·지휘 단계 문서).

## 4. 산출물 요구사항

최종 산출물은 두 가지다:

- **엑셀 회계장부**: 정제·분류 완료된 전체 거래 내역 — 카드(명의)별 구분, 카테고리 부여 상태
- **PDF 결산 리포트**: 월 단위 요약 — 카테고리별 지출 금액·비중 등
- 컬럼·목차 상세는 [인터페이스 정의서](interface-spec.md) "거래 표 스키마"·"산출물 양식" 참고

## 5. 비기능 요구사항

- **실데이터 보호**: 카드 실거래 데이터·credential은 repo에 커밋하지 않는다(.gitignore 차단 설정 완료, `sample_data/`만 허용). 개발·시연은 샘플 데이터로 한다.
- **로컬 우선**: 연동 계정 정보 등 민감 데이터는 로컬에만 존재하고 저장·전송하지 않는다.
- 기술 스택: Python (프레임워크·에이전트 구성은 폴더 구조 확정 시 결정)
