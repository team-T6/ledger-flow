# 지휘 에이전트 설계

> 담당: 김규은 · 상태: 초안 (지시서 기준으로 역이식 — 실행 중 검증 필요)
> 입출력의 정본은 [인터페이스 정의서](../interface-spec.md) — 여기에는 요약과 링크만 두고, 상세 스키마를 재정의하지 않는다.
> 이 문서는 이미 작성돼 있던 지시서([.claude/agents/orchestrator.md](../../.claude/agents/orchestrator.md))의 내용을 명세서 형식으로 옮긴 것이다. 원래 순서(명세 먼저, 지시서 나중)를 거꾸로 밟은 상태다.

## 1. 역할

월말결산 파이프라인 전체의 지휘자다. 실행 요청을 받으면 수집 → 가공 → 검증 1·2(병렬) → 통합을 순서대로 진행시키고, 각 단계의 결과 보고(인터페이스 정의서 "단계 결과 보고" JSON)만 읽어 다음 진행을 판단한다. 산출물 내용은 열어보지 않는다.

## 2. 입출력 요약

- 받는 것:
  - 파이프라인을 실행하고 싶다는 의미가 담긴 사용자의 요청 (예: "이번 달 결산 돌려줘")
  - 진행 중에는: 각 단계가 돌려주는 결과 보고 JSON — **단계 호출의 응답(반환값)으로 직접 받는다** (전달 방식 확정 → 상세는 [인터페이스 정의서](../interface-spec.md) "단계 결과 보고")
- 내놓는 것:
  - **최종 결과 요약** — `orchestrator/result-summary.md` (지휘가 실제로 새로 만드는 산출물은 이것 하나)
  - **회계 분석서 PDF·월 회계장부 엑셀** — 통합이 이미 `merge/`에 만든 산출물을 그대로 두고, 최종 결과 요약에서 그 경로(`merge/result.xlsx`·`merge/result.pdf`)로 안내한다. `orchestrator/`로 복사하지 않는다 (두는 자리 중복 방지)

## 3. 내부 처리 절차

1. **수집(collect)** 실행 → 결과 보고 확인
2. **가공(refine)** 실행 → 결과 보고 확인
3. **검증 1(verify1)·검증 2(verify2)** 병렬 실행 → 두 결과 보고 확인
4. **통합(merge)** 실행 → 결과 보고 확인
5. **최종 결과 요약** 작성 → 산출물과 함께 전달

각 단계 사이에서 `counts.total`을 대조해 거래 행 유실을 감지하고, 진행 내역을 실행 로그에 남긴다.

- run 디렉터리: 실행 시작 시각으로 `logs/run_YYYYMMDD_HHMMSS/`를 하나 만들어 이번 실행의 기록을 전부 그 안에 둔다 (실행 1회당 1디렉터리, 쓰는 주체는 지휘뿐 — [인터페이스 정의서](../interface-spec.md) "실행 로그 형식")
- 진행 로그 `run.log` 줄 형식: `시각 | 단계 | 상태(시작/완료/실패) | 처리 건수 | 메모` — 각 단계마다 호출 직전(시작)과 결과 보고 확인 직후(완료 또는 실패) 두 번 줄을 남긴다. 시작 줄은 처리 건수·메모가 빈 값, 완료·실패 줄은 그 단계 결과 보고의 `counts`·`message`를 옮겨 적는다
- 보고 아카이브: 각 단계가 반환한 결과 보고 원문을 `report-<단계>.json`으로 run 디렉터리에 저장한다 (재시도가 있었으면 두 번째 보고로 덮지 말고 `report-<단계>-retry.json`으로 나란히 남긴다)
- 최종 결과 요약 작성도 같은 `run.log`에 시작/완료 줄로 남긴다

## 4. 판단 규칙

- 판단할 것: 부분 실패 시 파이프라인을 중단할지 남은 단계를 계속 갈지
- 판단 기준:
  - `ok` → 다음 단계 진행
  - `empty` → 다음 단계 진행. **단, 수집이 `empty`면 특례로 이후 4단계를 호출하지 않고 "결산 대상 없음" 최종 요약으로 종료한다** (거래 0건이면 하류가 전부 헛돎)
  - `partial` → 진행하되 flagged 건을 요약의 "확인 필요 목록"에 싣는다. **대량 반려 경고**: `counts.flagged`가 `counts.total`의 50%를 초과하면(초기 임계값 — 운영하며 조정) 진행은 하되 최종 요약 맨 앞에 "대량 반려 — 원인 점검 필요" 경고를 싣는다
  - 검증 반려 건은 재시도 없이 통합의 "확인 필요" 목록으로 넘긴다 (확정 — 인터페이스 정의서 "지휘" 행 "못 할 때")
- **`failed` 처리 정책 (확정)**:
  - **재시도**: 어느 단계든 `failed`면 동일 입력으로 자동 재호출 **1회** (통합 포함, 전 단계 공통). 재시도도 `failed`면 확정하고, 두 번의 `message`를 모두 실행 로그와 최종 요약에 남긴다
  - **중단 범위** — 실패 위치 기준:
    | 실패 단계 | 동작 |
    |---|---|
    | 수집 · 가공 | 이후 단계 호출 없이 최종 요약 (하류 입력이 없음) |
    | 검증 1·2 중 하나 | 계속 진행 — 실패한 검증 자리는 "미완"으로 통합에 전달 (통합의 미완 흡수 설계 활용, 인터페이스 정의서 통합 행) |
    | 검증 1·2 둘 다 | 중단 후 최종 요약. 지휘가 두 `message`를 읽어 원인이 데이터가 아닌 환경 문제(기준 파일 부재 등)로 판단되면 요약에 "환경 조치 후 재실행 권고"를 명시한다 — 검증 없는 장부는 만들지 않는다 |
    | 통합 | 최종 결과 요약만 작성 |
  - `failed` 보고의 `message`는 필수 (인터페이스 정의서 "단계 결과 보고" — 빈 message면 "사유 미기재 실패"로 요약에 명시)
- 애매할 때 참조: 실행 로그·오류 내용
- 핵심 지시 (이 에이전트에게 시키는 말의 요지): "각 단계 결과 보고만 읽고 다음 진행을 판단하라. 산출물 내용은 열어보지 않는다. 어떤 이유로든 산출물을 못 만들어도 최종 결과 요약은 반드시 작성하라"

## 5. 오류·예외 처리

- 어떤 이유로든 산출물을 만들지 못해도 **최종 결과 요약은 반드시 작성**한다 — 어디까지 진행됐고 무엇이 왜 실패했는지를 요약에 담아 전달한다
- 단계가 `failed`를 보고하면 4장 확정 정책대로 처리한다 — 동일 입력 재호출 1회 후, 실패 위치 기준으로 중단 범위를 정한다
- 실행 로그는 커밋하지 않는다 (`logs/` 커밋 차단). 실데이터 커밋 금지 — 테스트는 `sample_data/` 가짜 데이터로만 한다

## 6. 사용 도구·의존성

- 이 프로젝트 폴더 안의 파일을 읽고 쓰는 것만 사용한다. 그 외 도구는 쓰지 않는다
- 결과를 만드는 데 코드가 필요하면 그 코드도 `orchestrator/` 폴더 안에 둔다
- 다른 5개 단계 에이전트(collect·refine·verify1·verify2·merge) 호출 계약 (확정): **호출 → 결과 보고(envelope) 반환**. 호출 계층에서 envelope JSON 스키마를 구조화 출력으로 강제하고, 형식 위반은 호출 실패로 처리한다. 실행 수단(call-agent 확장 등) 구현은 남은 과제 — 8장 참고

## 7. 테스트 방법

- `sample_data/` 기준 가공된 데이터 전체를 파이프라인에 흘려 각 단계 결과 보고가 정상 취합되고 `counts.total`이 유실 없이 대조되는지 확인한다
- 특정 단계를 `failed`로 강제한 시나리오로, 최종 결과 요약이 그래도 작성되는지 확인한다
- 검증 반려 건이 있는 시나리오로, 통합의 "확인 필요" 목록에 제대로 실리는지 확인한다

## 8. 막힌 점

- **파이프라인 루프 미구현** — 호출 계약은 확정됐으나(6장), 5개 단계를 순차 호출하며 envelope 스키마를 강제하고 run 디렉터리(로그·보고 아카이브)와 최종 결과 요약을 만드는 코드가 아직 없다. 현재 `orchestrator/call-agent.py`는 단발 호출(구조화 출력 없음)이라 확장이 필요하다
