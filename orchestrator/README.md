# 지휘 (orchestrator) — 이 칸의 약속

> 담당: 김규은 · 파이프라인 지휘
> 계약의 정본은 [인터페이스 정의서](../docs/interface-spec.md), 단계 내부 설계는 [설계서](../docs/agents/orchestrator.md), 에이전트에게 시키는 말은 [지시서](../.claude/agents/orchestrator.md).

## 하는 일

실행 요청을 받으면 수집 → 가공 → 검증 1·2(병렬) → 통합을 순서대로 진행시키고, 각 단계가 돌려주는 **결과 보고 JSON만 읽어** 다음 진행을 판단한다. 산출물 내용은 열어보지 않는다. 단계 사이에서 `counts.total`을 대조해 거래 행 유실을 감지하고, 진행 내역을 실행 로그(`logs/`)에 남긴다.

## 받는 것 / 내놓는 것

| | 내용 | 모양 |
|---|---|---|
| 받는 것 | 사용자의 실행 요청 + 각 단계의 결과 보고 JSON | [input-sample.md](input-sample.md) (규격 정본은 [인터페이스 정의서](../docs/interface-spec.md) "단계 결과 보고") |
| 내놓는 것 | 최종 결과 요약 | Markdown — [stub.md](stub.md) |

- 지휘가 새로 만드는 산출물은 **최종 결과 요약 하나**다. 회계 분석서 PDF·월 회계장부 엑셀은 통합이 `merge/`에 만든 것을 그대로 두고, 요약에서 경로로 안내만 한다 (이 칸으로 복사하지 않는다)
- 실행 로그는 `logs/run_YYYYMMDD_HHMMSS.log`에 실행 1회당 1파일로 남긴다 (형식은 [인터페이스 정의서](../docs/interface-spec.md) "실행 로그 형식")

## 이 칸의 파일

| 파일 | 무엇 |
|---|---|
| `README.md` | 이 문서 — 칸의 약속 |
| `input-sample.md` | 받는 재료 견본 — 단계 결과 보고 JSON 케이스별 견본 (가짜 데이터) |
| `stub.md` | 산출물 모양 견본 — 최종 결과 요약 (가짜 데이터) |
| `result-summary.md` | 진짜 산출물 — 실행하면 생김 |
| `result.md` | 초기 연습 실행 결과 (파일명 규칙 정리 전 산출물 — 참고용으로 유지) |
| `screen.html` | 연습 화면 |

칸 폴더를 옮기지 않고, 기존 파일을 지우지 않는다. 새 산출물은 견본 옆에 만든다.

## 판단 규칙 (요약)

상세는 [설계서 4장](../docs/agents/orchestrator.md)에 있다.

- `ok`·`empty` → 다음 단계 진행
- `partial` → 진행하되 flagged 건을 요약의 "확인 필요 목록"에 싣는다
- 검증 반려 건은 재시도 없이 통합의 "확인 필요" 목록으로 넘긴다 (확정 — 반려 루프 없음)
- `failed` → **정책 미정.** 지금은 잠정으로 재처리 없이 이후 단계를 호출하지 않고 곧바로 최종 결과 요약으로 넘어간다
- 어떤 이유로든 산출물을 못 만들어도 **최종 결과 요약은 반드시 작성**한다

## 미정 (팀 결정 대기)

- `failed` 처리 정책 — 실패 원인별 재처리 여부
- 서브에이전트(5개 단계) 호출 방식

## 지켜야 할 것

- **실데이터를 커밋하지 않는다.** 견본은 [sample_data/](../sample_data/) 기반 가짜 데이터로만 만든다 (개인 금융정보)
- 실행 로그는 커밋하지 않는다 (`logs/` 커밋 차단)
