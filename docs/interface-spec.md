## 파이프라인 인터페이스 표

주제: 여러 카드의 결제 내역을 모아 월 결산 산출물(엑셀 장부 + PDF 리포트) 만들기

> 각 단계가 "하는 것"(내부 처리)은 [PRD](PRD.md) §3과 각 에이전트 설계 문서(`agents/`) 몫 — 이 표는 단계 사이의 계약(무엇을·어떤 모양으로·어디에·안 될 땐 어떻게)만 다룬다.

| 단계 | 받는 것 | 내놓는 것 | 모양 | 두는 자리 | 못 할 때 |
|---|---|---|---|---|---|
| 수집 | Google Drive의 카드사 엑셀 + Google Drive·Photos의 OCR 대상 이미지 (영수증 사진·결제 문자 캡처 둘 다) | 표준 형식의 거래 내역 표 | CSV — 아래 "거래 표 스키마" (초안) | `collect/` | 원본이 없으면 "수집 대상 없음" 표시. OCR 인식 실패 건은 버리지 않고 오류 표시로 남김 |
| 가공 | 거래 내역 표 | 가맹점·카테고리가 붙은 거래 표 | **CSV** — 거래 표 스키마 동일, 결제처 정규화·카테고리 채움 (체계는 [categories.md](categories.md) 검토 중) | `refine/` | 가맹점 식별·분류 불가 건은 "확인 필요" 표시하고 버리지 않음 |
| 검증 1 | 가공된 거래 표 (검증 2와 같은 것을 동시에) | 항목별 통과·반려 결과 (분류 관점) | **CSV** — 입력 행에 판정·이유 열을 더한 모양, 항목마다 통과/반려 + 이유 한 줄 | `verify1/` | 검증할 항목이 없으면 "대상 없음" |
| 검증 2 | 가공된 거래 표 (검증 1과 같은 것을 동시에) | 항목별 통과·반려 결과 (기간·금액 관점) | **CSV** — 검증 1과 같은 모양(판정·이유 열 추가) | `verify2/` | 검증할 항목이 없으면 "대상 없음" |
| 통합 | 가공된 거래 표(CSV) + 두 검증 결과(CSV) | 엑셀 회계장부 + PDF 결산 리포트 (한 묶음) | 아래 "산출물 양식" — 장부는 거래 표 스키마, PDF 목차는 제안 검토 중. **중간 산출물(CSV)을 이 단계에서 바이너리(.xlsx·.pdf)로 변환하는 유일한 단계** | `merge/` | 앞 결과가 비거나 반려 미해결이면 그 자리에 "미완" 표시 + 사유 기재 |
| 지휘 | 각 단계의 결과 보고 (아래 "단계 결과 보고" 규격) | 최종 산출물 전달 + 실행 기록 | 아래 "실행 로그 형식" (제안 검토 중) | `logs/` | 어느 단계가 실패하면 중단하고 오류 보고. 검증 반려 건은 재시도 없이 통합의 "확인 필요" 목록으로 싣는다 (오류 보고 방식 확정 — 반려 루프 없음) |

> 두는 자리 확정: 단계 영어명 = repo 최상위의 "칸 폴더"명 (`collect/` `refine/` `verify1/` `verify2/` `merge/` — 담당자별 1칸). 각 칸 폴더에는 그 단계에 필요한 것이 전부 모인다: 약속(`README.md`) · 받는 재료 견본(`input-sample.md`) · 산출물 모양 견본(`stub.md`) · 진짜 산출물(`result.*`) · 산출물 생성에 코드가 필요하면 그 코드까지. 칸 폴더는 옮기지 않고, 기존 파일은 지우지 않는다.
>
> 커밋 정책: 견본(`input-sample.md`·`stub.md`)은 `sample_data/` 기반 가짜 데이터로만 작성해 커밋한다. **실데이터로 실행한 `result.*`는 커밋 금지** — .gitignore가 `*.xlsx`/`*.csv`/`*.pdf`를 차단하고 있어(`sample_data/` 제외) 기본적으로 걸러지며, 가짜 데이터 기반 결과를 공유하고 싶을 때만 팀 확인 후 예외로 올린다. 지휘의 실행 로그는 종전대로 `logs/`에 두고 커밋 차단(`logs/.gitkeep`만 커밋).

## 단계별 판단할 것

각 단계의 핵심 판단과, 애매할 때 참조할 곳. 상세 판단 규칙은 각 에이전트 설계 문서(`agents/`)에서 구체화한다.

| 단계 | 여기서 판단할 것 | 애매하면 무엇을 더 보나 |
|---|---|---|
| 수집 | OCR로 읽은 값이 거래 내역으로 맞는지 (금액·날짜 인식 오류 여부) | 원본 이미지·카드사 엑셀 원본 |
| 가공 | PG사 이름 뒤의 실제 가맹점이 어디인지, 어느 카테고리인지 | 원본 거래 내역의 부가 정보, 카테고리 체계 ([categories.md](categories.md) 검토 중) |
| 검증 1 | 부여된 카테고리가 체계에 맞는지 | 카테고리 체계 ([categories.md](categories.md) 검토 중) |
| 검증 2 | 대상 월 데이터가 맞는지, 해외결제 환산 금액이 맞는지, 지출/수익 컬럼이 행마다 하나만 채워졌는지 | 카드사 원본 내역 · 기준 환율 = 현금은 결제일 환율, 카드는 카드사 부여 환율 (추후 수정 상정) |
| 통합 | 어떤 구성으로 실어야 읽히는지 (장부 컬럼·리포트 목차) | 아래 "산출물 양식" 초안 |
| 지휘 | 부분 실패 시 파이프라인을 중단할지 남은 단계를 계속 갈지 | 실행 로그·오류 내용 |

## 거래 표 스키마 (초안)

수집이 만들어 통합까지 그대로 흐르는 공통 컬럼. **추후 수정 상정** — 바꿀 땐 이 표만 고치고 각 단계는 여길 따른다.

| 컬럼 | 설명 | 채우는 단계 |
|---|---|---|
| 날짜 | 결제일 | 수집 |
| 지출 | 지출 금액 (양수) — 행마다 지출·수익 중 하나만 채운다 | 수집 |
| 수익 | 수익 금액 (양수) — 상동, 둘 다 채워지면 오류 (검증 2 확인) | 수집 |
| 결제처 | 실제 가맹점명 — PG사 표기는 가공이 정규화 | 수집 → 가공 |
| 카테고리 | [categories.md](categories.md) 체계 (검토 중) | 가공 |
| 비고 | 부가 정보 (원문 표기·메모) | 수집·가공 |
| 결제수단 | 카드·현금 등 | 수집 |
| 결제자 | 결제수단 명의 (개인/법인 구분) | 수집 |

- 해외결제 환율: 현금 결제는 결제일 환율, 카드 결제는 카드사 부여 환율 기준 (추후 수정 상정)

## 산출물 양식 (초안)

- **엑셀 회계장부**: 거래 표 스키마와 동일 컬럼 (초안 — 추후 확정)
- **PDF 결산 리포트 목차 (제안 — 팀 검토)**:
	1. 결산 개요 — 대상 기간·카드, 총지출/총수익/순액
	2. 카테고리별 지출 — 금액·비중
	3. 결제수단별 합계
	4. 결제자(명의)별 합계 — 개인/법인 구분
	5. 주요 지출 Top 10
	6. 해외결제 명세 — 환산 내역
	7. 확인 필요 항목 — 검증 반려·미완·오류

## 단계 결과 보고 (제안)

모든 단계는 산출물과 별개로 **같은 형식의 결과 보고**(envelope pattern)를 지휘에게 돌려준다. 지휘는 이 보고만 읽고 다음 호출·중단·오류 처리를 판단하며, 산출물 내용은 열어보지 않는다.

```json
{
  "stage": "collect",
  "status": "ok",
  "output": "collect/202608_transactions.csv",
  "counts": { "total": 123, "ok": 120, "flagged": 3 },
  "flags": [
    { "row": 12, "type": "확인 필요", "reason": "가맹점 식별 불가" }
  ],
  "message": ""
}
```

- 필드 설명 (1뎁스):
	- `stage` — 보고 주체 (단계 영어명: `collect`·`refine`·`verify1`·`verify2`·`merge`)
	- `status` — 단계 전체 상태 (아래 4개 어휘 중 하나)
	- `output` — 산출물 파일 경로. 산출물 형식은 단계마다 다르며(인터페이스 표 "모양" 열) 이 필드는 경로만 담는다. 여러 개면 배열(예: 통합의 엑셀 + PDF), `empty`·`failed`면 빈 값
	- `counts` — 처리 건수 요약: `total` 입력 전체 · `ok` 정상 · `flagged` 문제 건. **단위는 전 단계 공통 "거래 행"** — 수집은 추출한 행, 검증은 검사한 행, 통합은 장부에 실은 행 (파일·이미지 개수는 `message`에). 단계 간 `total` 대조가 유실 감지의 근거
	- `flags` — 행 단위 문제 목록 (`row` 행 번호 · `type` 문제 유형 · `reason` 사유 한 줄)
	- `message` — 사람이 읽는 자유 메모 (실패 사유 등, 없으면 빈 값)
- `status` 어휘 (4개 고정):
	- `ok` — 정상 산출
	- `empty` — 처리할 대상 없음 ("수집 대상 없음"·"대상 없음"이 여기 대응)
	- `partial` — 산출했지만 flagged 건 있음 ("확인 필요"·"미완"·반려 건 포함)
	- `failed` — 단계 실패, 산출물 없음 (지휘는 중단·오류 보고)
- `flags[].type` 어휘: `확인 필요`(가공) · `반려`(검증) · `오류`(수집 OCR 실패 등) · `미완`(통합)
- 인터페이스 표의 "못 할 때" 문구는 사람용 표현이고, 이 보고가 그 기계 규격판이다. 보고는 지휘가 실행 로그에 그대로 기록한다.

## 실행 로그 형식 (제안)

- 파일: `logs/run_YYYYMMDD_HHMMSS.log` (실행 1회당 1파일)
- 줄 형식: `시각 | 단계 | 상태(시작/완료/실패) | 처리 건수 | 메모`

## 세는 법 메모

- 산출물 개수가 아니라 **갈라져 나가는 목적지 수**로 단계를 센다. 엑셀 장부 + PDF 리포트는 한 묶음으로 같은 곳에 전달되므로 통합은 한 단계.
- 검증 1·2는 같은 입력을 동시에 받는 병렬 구조 — 두 검증 리포트는 통합 전에 merge.
- 이후 웹 확장 등으로 산출물이 서로 다른 소비자에게 갈라지면 그때 단계를 쪼개고 분담표를 함께 고친다.

- 확정됨(2026-08-12 재검토): **수집→가공→검증 1→검증 2 사이의 중간 전달 형식은 CSV로 통일한다.** 이전에 "가공·검증 1은 엑셀(.xlsx)"로 합의했던 것을 이 결정으로 대체한다.
  - 이유: `collect`·`merge`·`orchestrator` 등 상당수 에이전트가 `Bash` 없이 `Read`/`Write`만으로 동작한다(`.claude/agents/*.md`의 `tools:` 참고) — 코드 실행 없이는 `.xlsx` 같은 바이너리 형식을 직접 열거나 만들 수 없고, CSV는 텍스트라 이 도구만으로도 다룰 수 있다
  - 예외: **최종 산출물(통합의 엑셀 회계장부 + PDF 결산 리포트)만 그대로 바이너리로 유지**한다 — 사람이 최종 결과물로 받는 문서이므로 CSV로 대체할 수 없다
  - 열린 과제: 통합(`merge`)이 CSV 입력을 실제 `.xlsx`·`.pdf`로 변환하려면 코드 실행 수단(예: `Bash` 도구 추가)이 필요하다 — 현재 `.claude/agents/merge.md`에는 없는 상태([docs/agents/merge.md](agents/merge.md) "막힌 점" 참고)
