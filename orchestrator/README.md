# 지휘 (orchestrator) — 이 칸의 약속

> 담당: 김규은 · 파이프라인 지휘 · 상태: 초안 (실행하며 검증 중)
> 계약의 정본은 [인터페이스 정의서](../docs/interface-spec.md), 단계 문서(설계+실행 지시의 단일 정본)는 [.claude/agents/orchestrator.md](../.claude/agents/orchestrator.md).

## 하는 일

실행 요청을 받으면 수집 → 가공 → 검증 1·2(병렬) → 통합을 순서대로 진행시키고, 각 단계가 돌려주는 **결과 보고 JSON만 읽어** 다음 진행을 판단한다. 산출물 내용은 열어보지 않는다. 단계 사이에서 `counts.total`을 대조해 거래 행 유실을 감지하고, 진행 내역을 실행 로그(`logs/`)에 남긴다.

## 받는 것 / 내놓는 것

| | 내용 | 모양 |
|---|---|---|
| 받는 것 | 사용자의 실행 요청 + 각 단계의 결과 보고 JSON (단계 호출의 응답으로 직접 받음) | [input-sample.md](input-sample.md) (규격 정본은 [인터페이스 정의서](../docs/interface-spec.md) "단계 결과 보고") |
| 내놓는 것 | 최종 결과 요약 | Markdown — [stub.md](stub.md) |

- 지휘가 새로 만드는 산출물은 **최종 결과 요약 하나**다. 회계 분석서 PDF·월 회계장부 엑셀은 통합이 `merge/`에 만든 것을 그대로 두고, 요약에서 경로로 안내만 한다 (이 칸으로 복사하지 않는다)
- 실행 기록은 `logs/run_YYYYMMDD_HHMMSS/`에 실행 1회당 1디렉터리로 남긴다 — 진행 로그(`run.log`) + 각 단계 보고 원문 아카이브(`report-<단계>.json`) (형식은 [인터페이스 정의서](../docs/interface-spec.md) "실행 로그 형식")

## 판단 규칙 (요약)

상세는 [단계 문서](../.claude/agents/orchestrator.md)에 있다.

- `ok`·`empty` → 다음 단계 진행 (단, 수집이 `empty`면 이후 호출 없이 "결산 대상 없음" 요약으로 종료)
- `partial` → 진행하되 flagged 건을 요약의 "확인 필요 목록"에 싣는다 (반려율 50% 초과면 요약 맨 앞에 "대량 반려" 경고)
- 검증 반려 건은 재시도 없이 통합의 "확인 필요" 목록으로 넘긴다 (확정 — 반려 루프 없음)
- `failed` → 동일 입력 재호출 1회 후 실패 위치 기준 처리: 수집·가공은 이후 중단, 검증 편측은 "미완"으로 진행, 검증 양측은 중단, 통합은 요약만 (`failed`의 `message`는 필수)
- 어떤 이유로든 산출물을 못 만들어도 **최종 결과 요약은 반드시 작성**한다

## 미정 (팀 결정 대기)

- 서브에이전트(5개 단계) 호출 방식 — 단발 호출 패턴(`call-agent.py`)은 있으나 파이프라인 순차 호출 루프는 미구현

## 지켜야 할 것

- **실데이터를 커밋하지 않는다.** 견본은 [sample_data/](../sample_data/) 기반 가짜 데이터로만 만든다 (개인 금융정보)
- 실행 로그는 커밋하지 않는다 (`logs/` 커밋 차단)

## 테스트 방법

- `sample_data/` 기준 가공된 데이터 전체를 파이프라인에 흘려 각 단계 결과 보고가 정상 취합되고 `counts.total`이 유실 없이 대조되는지 확인한다
- 특정 단계를 `failed`로 강제한 시나리오로, 최종 결과 요약이 그래도 작성되는지 확인한다
- 검증 반려 건이 있는 시나리오로, 통합의 "확인 필요" 목록에 제대로 실리는지 확인한다
