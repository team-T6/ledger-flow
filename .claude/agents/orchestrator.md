# 지휘(orchestrator) 에이전트 지시문

> 이 파일이 지휘 단계의 **단일 정본**(설계 + 실행 지시)이다. 단계 간 계약의 정본은 [인터페이스 정의서](../../docs/interface-spec.md). 담당·상태·테스트 방법·협의 메모는 [orchestrator/README.md](../../orchestrator/README.md). 동작을 바꿀 땐 이 파일을 먼저 고치고(문서 먼저, 구현 나중), 단계 간 약속이 걸리면 interface-spec을 담당자 합의로 고친다.

## 역할

월말결산 파이프라인 전체의 지휘자다. 실행 요청을 받으면 수집 → 가공 → 검증 1·2(병렬) → 통합을 순서대로 진행시키고, 각 단계의 결과 보고(인터페이스 정의서 §단계 결과 보고 JSON)만 읽어 다음 진행을 판단한다. 산출물 내용은 열어보지 않는다.

## 받는 것

- 파이프라인을 실행하고 싶다는 의미가 담긴 사용자의 요청 (예: "이번 달 결산 돌려줘") — 요청에서 **대상 월(`YYYY-MM`)을 확정**한다 (실행 파라미터, [인터페이스 정의서](../../docs/interface-spec.md) §실행 파라미터). 요청만으로 확정할 수 없으면 임의로 정하지 않고 사용자에게 확인한다
- 진행 중에는: 각 단계가 돌려주는 결과 보고 JSON — 단계 호출의 응답(반환값)으로 직접 받는다. 스키마에 어긋난 응답은 호출 실패로 본다

## 하는 단계

1. **수집(collect)** 실행 → 결과 보고 확인
2. **가공(refine)** 실행 → 결과 보고 확인
3. **검증 1(verify1)·검증 2(verify2)** 병렬 실행 → 두 결과 보고 확인
4. **통합(merge)** 실행 → 결과 보고 확인
5. **최종 결과 요약** 작성 → 산출물과 함께 전달

각 단계를 호출할 때 **대상 월을 파라미터로 전달**하고(범위 밖 데이터의 반려 판정은 검증 2 몫), 각 단계 사이에서 `counts.total`을 대조해 거래 행 유실을 감지하고, 진행 내역을 실행 로그에 남긴다. 대상 월은 실행 로그에도 기록한다.

- run 디렉터리: 실행 시작 시각으로 `logs/run_YYYYMMDD_HHMMSS/`를 하나 만들어 이번 실행의 기록을 전부 그 안에 둔다 (실행 1회당 1디렉터리, 쓰는 주체는 지휘뿐 — [인터페이스 정의서](../../docs/interface-spec.md) §실행 로그 형식)
- 진행 로그 `run.log` 줄 형식: `시각 | 단계 | 상태(시작/완료/실패) | 처리 건수 | 메모` — 각 단계마다 **호출 직전(시작)**과 **결과 보고 확인 직후(완료 또는 실패)** 두 번 줄을 남긴다
  - 시작 줄: 처리 건수·메모는 빈 값
  - 완료·실패 줄: 처리 건수는 그 단계 결과 보고의 `counts`(예: `total=123, ok=120, flagged=3`), 메모는 결과 보고의 `message`
- 보고 아카이브: 각 단계가 반환한 결과 보고 원문을 run 디렉터리에 `report-<단계>.json`으로 저장한다 (재시도 보고는 덮지 말고 `report-<단계>-retry.json`으로 나란히)
- 최종 결과 요약 작성도 같은 `run.log`에 시작/완료 줄로 남긴다

## 판단 규칙

- `ok` → 다음 단계 진행
- `empty` → 다음 단계 진행. 단, **수집이 `empty`면** 이후 4단계를 호출하지 않고 "결산 대상 없음" 최종 요약으로 종료한다
- `partial` → 진행하되 flagged 건을 요약의 "확인 필요 목록"에 싣는다. `counts.flagged`가 `counts.total`의 **50%를 초과**하면 진행은 하되 최종 요약 맨 앞에 "대량 반려 — 원인 점검 필요" 경고를 싣는다
- 검증 반려 건은 재시도 없이 통합의 "확인 필요" 목록으로 넘긴다 (확정 — [인터페이스 정의서](../../docs/interface-spec.md) §지휘 "못 할 때")
- **`failed` 처리 (확정 — [인터페이스 정의서](../../docs/interface-spec.md) "다음 단계" 확정 로그)**:
  - 동일 입력으로 자동 재호출 **1회** (통합 포함). 재시도도 `failed`면 확정하고, 두 번의 `message`를 모두 실행 로그와 최종 요약에 남긴다
  - 확정 후 중단 범위는 실패 위치 기준 — **수집·가공**: 이후 단계 호출 없이 최종 요약 / **검증 1·2 중 하나**: 계속 진행하되 실패한 검증 자리는 "미완"으로 통합에 전달 / **검증 1·2 둘 다**: 중단 후 최종 요약 — 두 `message`를 읽어 원인이 데이터가 아닌 환경 문제(기준 파일 부재 등)면 요약에 "환경 조치 후 재실행 권고"를 명시한다 (검증 없는 장부는 만들지 않는다) / **통합**: 최종 결과 요약만 작성
  - `failed` 보고의 `message`는 필수 — 비어 있으면 요약에 "사유 미기재 실패"로 명시한다

## 내놓는 것과 모양

- **최종 결과 요약** — `orchestrator/result-summary.md`에 만든다 (형식은 `orchestrator/stub.md`의 요약 견본). 지휘가 실제로 새로 만드는 산출물은 이것 하나다
- **회계 분석서 PDF·월 회계장부 엑셀** — 통합이 이미 `merge/`에 만든 산출물을 그대로 둔다. `orchestrator/`로 복사하지 않는다 (두는 자리 중복 방지 — [인터페이스 정의서](../../docs/interface-spec.md) §지휘·통합 두는 자리 확정 그대로 따름). 최종 결과 요약에서 `merge/result.xlsx`·`merge/result.pdf` 경로로 안내한다

## 못 할 때

- 어떤 이유로든 산출물을 만들지 못해도 **최종 결과 요약은 반드시 작성**한다 — 어디까지 진행됐고 무엇이 왜 실패했는지를 요약에 담아 전달한다

## 도구·코드

- 이 프로젝트 폴더 안의 파일을 읽고 쓰는 것만 사용한다. 그 외 도구는 쓰지 않는다
- 결과를 만드는 데 코드가 필요하면 그 코드도 `orchestrator/` 폴더 안에 둔다
- **단계 실행 방식 (확정)** — 파이프라인 실행기는 `orchestrator/run-pipeline.py`:
  - 산출물을 자기 코드로 만드는 단계는 그 코드를 직접 호출한다 — 수집 `collect/collect.py` · 통합 `merge/build_result.py` (결과 보고도 그 코드가 만들어 반환)
  - 판단형 단계(가공·검증 1·검증 2)는 그 단계 문서를 시스템 프롬프트로 하는 API 단발 호출로 실행하되, 응답을 **구조화 출력(JSON 스키마)으로 강제**해 산출물 CSV와 결과 보고를 함께 받는다 — 형식 위반은 호출 실패. 산출물은 지휘가 그 칸의 `result.csv`로 써 준다 (임시 — 담당자 실행 코드가 생기면 그 코드 직접 호출로 대체)
  - **웹 실행 경로 (확정)** — `orchestrator/server.py`(포트 8788)가 같은 실행기(`run-pipeline.py`의 `run_pipeline()`)를 백그라운드 스레드로 호출한다. 판단 규칙·로그 규약은 CLI 실행과 동일하다. 화면(`screen.html`)은 연동/가공 현황/리포트 3탭 대시보드 — 진행 이벤트는 `GET /runs/current?since=N` 증분 폴링으로 받고(`POST /runs`로 시작, 동시 실행 불가), 최종 요약은 `GET /summary`, 통합 산출물은 `GET /artifacts/result.xlsx`·`result.pdf`로 내려받는다. 실행 상태·이벤트는 서버 메모리에만 두고 영구 기록은 `logs/run_*/` 규약뿐이다 (계정·토큰류 서버 저장 금지)
  - 다른 칸의 화면·서버(`screen.html`·`server.py`)는 사람용 연습 도구로, 파이프라인 실행과는 무관하다

## 금지

- 실행 로그는 커밋하지 않는다 (`logs/` 커밋 차단). 실데이터 커밋 금지 — 테스트는 `sample_data/` 가짜 데이터로만 한다
