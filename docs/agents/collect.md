# 수집 에이전트 설계

> 담당: 이승환 · 상태: 초안 (지시서 기준으로 역이식 — 실행 중 검증 필요)
> 입출력의 정본은 [인터페이스 정의서](../interface-spec.md) — 여기에는 요약과 링크만 두고, 상세 스키마를 재정의하지 않는다.
> 이 문서는 이미 작성돼 있던 지시서([.claude/agents/collect.md](../../.claude/agents/collect.md))의 내용을 명세서 형식으로 옮긴 것이다. 원래 순서(명세 먼저, 지시서 나중)를 거꾸로 밟은 상태라, 담당자가 내용을 검토·보완해야 한다.

## 1. 역할

카드사 Excel/CSV와 영수증 이미지·결제 문자 캡처를 바탕으로 거래 정보를 선행 수집하고, 카드사 내역으로 검증·보완해 표준 거래 표(CSV)를 만든다. 파이프라인의 첫 단계이며 결과는 가공(refine) 단계로 넘어간다.

## 2. 입출력 요약

- 받는 것:
  - Google Drive의 카드사 Excel/CSV (카드사마다 컬럼 형식이 다르고, 법인카드·개인카드가 섞여 들어올 수 있다) — 실제 연동 전까지 테스트 자리는 `sample_data/hana_card/`의 더미 데이터
  - Google Drive·Photos의 영수증 이미지·결제 문자 캡처 (OCR 대상) — 사용자가 그 자리에서 촬영해 올리는 사진도 같은 경로로 들어온다
  - (→ 상세는 [인터페이스 정의서](../interface-spec.md) "수집" 행)
- 내놓는 것: 표준 거래 표(CSV) — `collect/result.csv` (칸 폴더 공용 관례 `result.*`, AGENTS.md §2). 컬럼: `transaction_id`·날짜·지출·수익·결제처·비고·결제수단·결제자·`source_type`·`collect_status`·**`구매항목`** (카테고리는 가공 단계 몫, 공통 스키마 7컬럼은 [인터페이스 정의서](../interface-spec.md) "거래 표 스키마" 순서 그대로, 앞에 `transaction_id`, 맨 뒤에 수집 전용 필드 3개 — `source_type`·`collect_status`·`구매항목` — 를 덧붙인 모양). `구매항목`은 가공이 카테고리를 정할 때 결제처만으론 애매한 건(마트·편의점 등)을 보완하는 용도 — 가공 담당 요청으로 추가, `collect_status` 바로 뒤(맨 끝)에 둔다

## 3. 내부 처리 절차

1. 카드사 Excel/CSV가 들어오면 카드사별 컬럼 매핑 규칙으로 표준 필드(날짜·금액·가맹점·결제수단·결제자)로 정규화한다. 매핑 규칙이 없는 낯선 서식이면 임의로 해석하지 않고 확인 필요로 표시한다
2. 새 영수증 이미지를 감지하고 File Hash로 중복이면 skip한다 (촬영 즉시 업로드된 사진도 동일하게 신규 이미지로 감지된다)
3. 신규 이미지는 Vision/OCR로 거래일·금액·결제처·결제수단·구매 물품 목록(`구매항목`)을 추출한다 — 물품이 여럿이면 콤마로 구분
4. 추출값으로 기존 거래를 검색해 동일 거래면 이미지를 연결하고, 신규면 `transaction_id`(`tx_{YYMMDD}_{순번}`)를 부여해 pending으로 등록한다
5. 정규화된 카드사 내역을 날짜+금액+결제처+결제수단 기준으로 기존 거래와 매칭한다 (표기가 다르면 유사도로 추가 판단)
6. 일치하면 검증 완료 처리, 카드 내역에만 있으면 신규 거래로 추가, 불명확하면 review로 표시한다
7. 현금 등 자동 수집이 어려운 거래는 사용자 직접 입력을 받아 같은 형식으로 반영한다
8. OCR 인식 실패 건과 서식 인식 실패 건은 버리지 않고 오류/확인 필요로 표시해 남긴다

## 4. 판단 규칙

- 판단할 것:
  - OCR로 읽은 값이 거래로 맞는지 (금액·날짜 인식 오류 여부)
  - 영수증과 카드사 내역이 같은 거래인지 (날짜+금액+결제처+결제수단, 표기가 다르면 유사도 판단)
  - 이 거래가 법인카드인지 개인카드인지 (`결제자` 필드로 구분 — 등록된 카드 목록의 명의 기준, 애매하면 확인 필요로 남긴다)
- 판단 기준: 카드사별 컬럼 매핑 규칙(정규화) + 날짜·금액·결제처·결제수단 4개 축 매칭
- 애매할 때 참조: 원본 이미지·카드사 엑셀 원본 (인터페이스 정의서 "단계별 판단할 것" 수집 행)
- 핵심 지시 (이 에이전트에게 시키는 말의 요지): "낯선 서식·인식 실패·매칭 불확실 건은 임의로 끼워 맞추지 말고 확인 필요/review로 남겨라. 표준 컬럼은 카드사가 늘어도 바뀌지 않는다"
- AI 판단이 필요한 곳 / 일반 코드로 처리할 곳:
  - 일반 코드 — 카드사 컬럼 매핑(정규화 규칙이 있는 서식), File Hash 중복 판정, 날짜/금액 정확 일치 매칭, 결과 CSV 작성
  - AI 판단 — 영수증 Vision/OCR 추출, 표기가 다를 때의 유사도 판단, 매핑 규칙 없는 낯선 서식 감지

## 5. 오류·예외 처리

- 원본이 없으면 "수집 대상 없음"으로 표시한다
- 매핑 규칙이 없는 낯선 카드사 서식이면 임의로 표준 필드에 끼워 맞추지 않고 확인 필요로 표시한다 — 새 매핑 규칙 추가는 사람이 판단
- OCR 인식 실패 건은 버리지 않고 오류 표시로 남긴다
- 영수증-카드내역 매칭이 불확실하면 반려 대신 review로 남긴다
- 영수증이 없거나(카드사 내역만으로 수집된 건) 아직 확인 전이면 `구매항목`은 빈칸으로 둔다 — 없는 물품 목록을 지어내지 않는다
- 실패를 조용히 삼키지 않는다 (공통 규칙 AGENTS_COM.md §4)

## 6. 사용 도구·의존성

- 언어: Python (프로젝트 공통 — 버전·패키지 매니저 미정)
- OCR/Vision 도구: 미정 — 영수증·결제 문자 캡처 인식에 쓸 구체 서비스/모델 확정 필요
- Google Drive·Photos 연동 방식: 미정 — API 인증 방식 확정 필요

## 7. 테스트 방법

`sample_data/hana_card/`의 더미 하나카드 데이터로 테스트한다 (실데이터 사용 금지 — AGENTS.md §8).

| 샘플 입력 | 기대 출력 |
|---|---|
| `sample_data/hana_card/2026-02_하나카드_이용내역서.csv` (일시불 거래) | 표준 컬럼으로 정규화된 행, `collect_status`=`확인됨` |
| 6개월 할부 거래(하이마트, 최초 구매 2026-02-10) | 회차마다 같은 `transaction_id`, `날짜`·`지출`만 회차별로 갱신 |
| 영수증 선행 수집 → 이후 카드 내역 매칭 | 매칭 전 `collect_status`=`대기`, 매칭 후 `확인됨`으로 갱신되며 `transaction_id` 유지 |
| 매핑 규칙 없는 낯선 카드사 서식 | 확인 필요로 표시, 임의 정규화하지 않음 |
| 영수증으로 구매 물품까지 확인된 거래(`collect_status`=`확인됨`) | `구매항목`에 물품 목록(콤마 구분) 채움 |
| 아직 확인 전인 거래(`collect_status`=`확인 필요`) | `구매항목` 빈칸 |

견본 파일(`collect/input-sample.md`·`collect/stub.md`)도 이 가짜 데이터 기준으로 만든다.

## 8. 막힌 점

- **OCR/Vision 도구 미확정** — 영수증·결제 문자 캡처 인식에 쓸 서비스·모델을 팀에서 정해야 한다
- **영수증 이미지 견본 없음** — `collect/input-sample.md`에 카드사 Excel/CSV 예시만 있고, 이미지 원천은 텍스트로 대체할 수 없어 아직 견본이 없다. OCR 처리 확인이 필요해지면 실제 이미지 견본을 별도 준비해야 한다
- **법인카드 실데이터 없음** — 지금 더미 데이터는 개인카드(하나카드)뿐이라 법인/개인 판별 로직이 실제로 검증되지 않았다
- **`구매항목` 추출 로직 미검증** — 실제 영수증 이미지·OCR이 없어(위 "영수증 이미지 견본 없음"과 같은 이유) 더미 데이터의 `구매항목`은 사람이 채운 가짜 값이다. 실제 OCR 연동 시 추출 정확도·물품명 정규화 방식을 다시 검토해야 한다
