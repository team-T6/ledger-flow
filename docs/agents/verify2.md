# 검증 2 에이전트 설계

> 담당: 이지은 · 상태: 초안
> 입출력의 정본은 [인터페이스 정의서](../interface-spec.md) — 여기에는 요약과 링크만 두고, 상세 스키마를 재정의하지 않는다.

## 1. 역할

가공된 거래 표를 받아 **기간·금액 관점**에서 기준 적합성을 검증한다 (분류 관점은 검증 1 담당). 검증 1과 같은 입력을 동시에 받는 병렬 구조이며, 재시도 없이 통과/반려 결과만 낸다.

## 2. 입출력 요약

- 받는 것: `data/refine/`의 가공된 거래 표 (검증 1과 동일 입력), **CSV** → 스키마 상세는 [interface-spec.md 거래 표 스키마](../interface-spec.md#거래-표-스키마-초안)
- 내놓는 것: 거래 행별 통과/반려 결과 (이유 한 줄 포함), **CSV** → `data/verify/` (검증 1과 파일 구분) — 2026-08-12 interface-spec.md에 공식 확정된 내용 (근거 있음)

## 3. 내부 처리 절차

1. `data/refine/`에서 대상 월의 가공된 거래 표를 로드한다.
2. 각 행에 대해 §4의 세 가지 판단 기준을 순서대로 적용한다 (월 확인 → 단일 기입 확인 → 해외결제 환산 확인). 한 행에서 여러 기준이 동시에 걸리면 모두 기록한다 (하나만 걸리고 끝내지 않는다).
3. 행별 결과(통과/반려 + 사유)를 누적해 검증 결과 표를 만든다.
4. 결과 표를 `data/verify/`에 CSV로 저장한다.
5. §5 규격의 단계 결과 보고(JSON envelope)를 만들어 지휘에게 반환한다.

## 4. 판단 규칙

- 판단할 것 ①: **대상 월 데이터인지**
  - 기준: 행의 `날짜` 컬럼이 이번 결산 대상 월(YYYY-MM) 범위 안인지 확인. 범위 밖이면 반려, 사유 `"대상 월 아님 (날짜: {값})"`.
  - 애매할 때 참조: 대상 월 값 자체 — **실행 파라미터로 어떻게 전달받는지 인터페이스 정의서에 아직 없음 (§8 참고)**.

- 판단할 것 ②: **지출/수익 단일 기입인지**
  - 기준: 지출/수익 컬럼(하나의 카테고리 컬럼, 값은 '지출' 또는 '수익')에 값이 명확히 하나 들어있는지 확인. 비어 있으면 반려, 사유 `"지출/수익 미기입"`. '지출'·'수익' 외의 값이거나 형식이 불명확하면 반려, 사유 `"지출/수익 구분 불명확"`.
  - **※ interface-spec.md 공식 스키마는 지출·수익이 별도 두 컬럼으로 되어 있으나, 영진님과 구두로 하나의 컬럼으로 합의함 (2026-08-12). interface-spec.md는 아직 미반영 상태.**

- 판단할 것 ③: **해외결제 원화 환산이 맞는지**
  - 기준: 현금 결제는 결제일 환율, 카드 결제는 카드사 부여 환율로 재계산한 금액과 `지출`/`수익` 컬럼 값을 비교. 오차 허용 범위 밖이면 반려, 사유 `"환산 금액 불일치 (기록: {값}, 재계산: {값})"`.
  - 애매할 때 참조: 카드사 원본 내역·기준 환율표
  - **막힘**: 거래 표 스키마([interface-spec.md](../interface-spec.md#거래-표-스키마-초안))에 해외결제 여부·원거래통화·원거래금액 컬럼이 없어, 국내/해외 결제 구분과 환산 전 원금액을 지금 스키마만으로는 식별할 수 없음 (§8 참고).

- 참고: 결제구분 컬럼(값: '개인결제'·'법인결제')이 결제자 컬럼을 대체한다. 검증 2의 판단 기준 세 가지에는 직접 사용하지 않는다 (참고 정보).

- 핵심 지시 (이 에이전트에게 시키는 말의 요지): "가공된 거래 표를 대상 월·단일 기입·해외 환산 세 기준으로 훑어서, 걸리는 행마다 통과/반려와 사유 한 줄을 남겨라. 정정하지 말고 반려만 하라."

## 5. 오류·예외 처리

- 입력 표 자체가 없거나 비어 있으면 → 단계 결과 보고 `status: "empty"`, `message: "검증 대상 없음"` (재시도 없음, interface-spec.md "못 할 때" 규격 그대로).
- 필수 컬럼(`날짜`·`지출`·`수익`·`결제수단`)이 누락된 입력이면 → 검증을 진행하지 않고 `status: "failed"`로 즉시 지휘에게 보고하고, `message`에 누락된 컬럼을 명시한다 (`failed`의 `message`는 필수 — interface-spec.md "단계 결과 보고" 확정 규격. 조용히 건너뛰지 않는다).
- 개별 행에서 판단이 불가능한 경우(예: 날짜 형식이 깨짐)는 반려가 아니라 별도 사유(`"판단 불가 (형식 오류)"`)로 flag하여 사람이 확인하게 한다 — 임의로 통과 처리하지 않는다.

## 7. 테스트 방법

- `sample_data/`에 검증 2 판단 기준 세 가지를 각각 걸리게/안 걸리게 설계한 샘플 가공 거래 표를 두고, 기대 결과(행별 통과/반려 + 사유)와 대조한다. **`sample_data/`가 현재 비어 있어 샘플 준비가 선행되어야 함** (PRD §6 열린 질문과 동일 블로커).
- 실데이터로 테스트하지 않는다.

## 8. 막힌 점

1. **거래 표 스키마에 해외결제 식별 정보 부재**: 판단 기준 ③(해외결제 환산 검증)을 수행하려면 해외결제 여부·원거래통화·원거래금액이 필요한데, 현재 [거래 표 스키마](../interface-spec.md#거래-표-스키마-초안)엔 없음. 수집·가공 담당과 스키마에 컬럼 추가를 논의해야 함.
2. **대상 월 파라미터 전달 방식 미정**: 검증 2가 "대상 월"을 어떻게 받는지(오케스트레이터 실행 인자? 설정 파일?) interface-spec.md에 정의돼 있지 않음. 지휘(오케스트레이터) 담당과 확인 필요.
3. **검증 결과 파일 형식(CSV) — 통합 담당과 합의 필요**: 이 문서 §3·§4에서는 CSV로 제안했으나, interface-spec.md "다음 단계"에 "검증 결과의 파일 형식(CSV vs JSON) 미정 — 통합이 merge하기 쉬운 쪽으로"라고 명시돼 있음. 통합 담당(박인혜)과 합의되기 전까지는 제안 단계이며, 합의되면 interface-spec.md도 함께 갱신해야 함 (AGENTS.md §9 문서 위계 규칙).
4. 영진님(가공)과 구두로 합의한 스키마 변경사항 — 2026-08-12: 지출/수익 단일 카테고리 컬럼(§4②에 반영), 결제자 컬럼 제외하고 결제구분 컬럼(개인결제/법인결제 값) 신설(§4에 반영). 이는 interface-spec.md 공식 스키마(지출·수익 별도 컬럼, 결제자=명의)와 다름. interface-spec.md는 아직 갱신 안 됨 — 영진님과 함께 팀 전체 합의로 공식 반영 필요 (AGENTS.md §9 문서 위계 규칙).
