## 파이프라인 인터페이스 표

주제: 여러 카드의 결제 내역을 모아 월 결산 산출물(엑셀 장부 + PDF 리포트) 만들기

> 각 단계가 "하는 것"(내부 처리)은 [PRD](PRD.md) §3과 각 단계 문서(`.claude/agents/`) 몫 — 이 표는 단계 사이의 계약(무엇을·어떤 모양으로·어디에·안 될 땐 어떻게)만 다룬다.

| 단계 | 받는 것 | 내놓는 것 | 모양 | 두는 자리 | 못 할 때 |
|---|---|---|---|---|---|
| 수집 | Google Drive의 카드사 엑셀 + Google Drive·Photos의 OCR 대상 이미지 (영수증 사진·결제 문자 캡처 둘 다) + 웹 화면에서 직접 올린 파일(`uploads/inbox/` — CSV/TXT/이미지/XLSX/PDF, zip 압축 포함(수집이 풀어서 처리)) | 표준 형식의 거래 내역 표 | CSV — 아래 "거래 표 스키마" (확정 v1) | `collect/` | 원본이 없으면 "수집 대상 없음" 표시. OCR 인식 실패 건은 버리지 않고 오류 표시로 남김. 텍스트 레이어 없는(스캔) PDF는 추출 실패로 오류 표시. zip 안에서 허용되지 않는 서식·zip 안의 zip·경로 탈출 항목은 건너뛰고 오류로 남김 |
| 가공 | 거래 내역 표 | 가맹점·카테고리가 붙은 거래 표 | **CSV** — 거래 표 스키마 동일, 결제처 정규화·카테고리 채움 (체계는 [categories.md](categories.md) 확정) | `refine/` | 가맹점 식별·분류 불가 건은 "확인 필요" 표시하고 버리지 않음 |
| 분류 검증 | 가공된 거래 표 (기간·금액 검증과 같은 것을 동시에) | 항목별 통과·반려 결과 (분류 관점) | **CSV** — 입력 행 뒤에 판정 열 `verify1_result`(`통과`/`반려`)·이유 열 `verify1_reason`(반려 사유 한 줄, 통과면 빈칸)을 덧붙인 모양 (확정). 행을 지우거나 순서를 바꾸지 않고, 행 대조 키는 `transaction_id` | `verify1/` | 검증할 항목이 없으면 "대상 없음" |
| 기간·금액 검증 | 가공된 거래 표 (분류 검증과 같은 것을 동시에) | 항목별 통과·반려 결과 (기간·금액 관점) | **CSV** — 분류 검증과 같은 모양(확정): 판정 열 `verify2_result`·이유 열 `verify2_reason` | `verify2/` | 검증할 항목이 없으면 "대상 없음" |
| 부정 사용 검증 | 가공된 거래 표 (분류/기간·금액 검증과 같은 것을 동시에 — **부정 사용 감지 토글을 켠 실행만**) | 항목별 통과·확인 요청 결과 (법인카드 부정 사용 관점 — 법인결제 행만 판정, 개인결제 행은 판정 없이 통과) | **CSV** — 분류/기간·금액 검증과 같은 모양(확정): 판정 열 `verify3_result`(`통과`/`확인 요청`)·이유 열 `verify3_reason`. 부정 사용을 단정하지 않고 `확인 요청`으로만 표시 (기준은 [fraud-rules.md](fraud-rules.md) 확정) | `verify3/` | 검증할 항목이 없으면 "대상 없음", 법인결제 행이 없으면 전 행 통과 + "판정 대상 없음" 메모 |
| 통합 | 가공된 거래 표(CSV) + 검증 결과(CSV — 분류/기간·금액 검증, 토글 켠 실행은 부정 사용 검증 포함) + 과거 월 집계(`archive/<월>/summary.json`, 있으면 — 전월 대비·월별 추이용, 읽기 전용) | 엑셀 회계장부 + PDF 결산 리포트 (한 묶음) | 아래 "산출물 양식" (확정) — 장부는 거래 표 스키마, PDF 목차 확정. **중간 산출물(CSV)을 이 단계에서 바이너리(.xlsx·.pdf)로 변환하는 유일한 단계** | `merge/` | 앞 결과가 비거나 반려 미해결이면 그 자리에 "미완" 표시 + 사유 기재 |
| 지휘 | 각 단계의 결과 보고 (아래 "단계 결과 보고" 규격) | 최종 산출물 전달 + 실행 기록 | 아래 "실행 로그 형식" | `logs/` | `failed`면 동일 입력으로 1회 재호출 후 실패 위치 기준 처리 (사용량 한도 초과 실패는 재시도 생략 — 리셋 전엔 같은 결과) — 수집·가공은 이후 중단, 검증 편측은 그 자리 "미완"으로 진행, 검증 양측은 중단, 통합은 요약만 (상세는 [.claude/agents/orchestrator.md](../.claude/agents/orchestrator.md) "판단 규칙"). 수집이 `empty`면 이후 단계 호출 생략. 검증 반려 건은 재시도 없이 통합의 "확인 필요" 목록으로 싣는다 (반려 루프 없음) |

> 두는 자리 확정: 단계 영어명 = repo 최상위의 "칸 폴더"명 (`collect/` `refine/` `verify1/` `verify2/` `verify3/` `merge/` — 담당자별 1칸). 각 칸 폴더에는 그 단계에 필요한 것이 전부 모인다: 약속(`README.md`) · 받는 재료 견본(`input-sample.md`) · 산출물 모양 견본(`stub.md`) · 진짜 산출물(`result.*`) · 산출물 생성에 코드가 필요하면 그 코드까지. 칸 폴더는 옮기지 않고, 기존 파일은 지우지 않는다.
>
> 커밋 정책: 견본(`input-sample.md`·`stub.md`)은 `sample_data/` 기반 가짜 데이터로만 작성해 커밋한다. **실데이터로 실행한 `result.*`는 커밋 금지** — .gitignore가 `*.xlsx`/`*.csv`/`*.pdf`를 차단하고 있어(`sample_data/` 제외) 기본적으로 걸러지며, 가짜 데이터 기반 결과를 공유하고 싶을 때만 팀 확인 후 예외로 올린다. 지휘의 실행 로그는 종전대로 `logs/`에 두고 커밋 차단(`logs/.gitkeep`만 커밋).

## 단계별 판단할 것

각 단계의 핵심 판단과, 애매할 때 참조할 곳. 상세 판단 규칙은 각 단계 문서(`.claude/agents/<단계>.md`)에서 구체화한다.

| 단계 | 여기서 판단할 것 | 애매하면 무엇을 더 보나 |
|---|---|---|
| 수집 | OCR로 읽은 값이 거래 내역으로 맞는지 (금액·날짜 인식 오류 여부) | 원본 이미지·카드사 엑셀 원본 |
| 가공 | PG사 이름 뒤의 실제 가맹점이 어디인지, 어느 카테고리인지 | 원본 거래 내역의 부가 정보, 카테고리 체계 ([categories.md](categories.md) 확정) |
| 분류 검증 | 부여된 카테고리가 체계에 맞는지 | 카테고리 체계 ([categories.md](categories.md) 확정) |
| 기간·금액 검증 | 대상 월 데이터가 맞는지, 해외결제 환산 환율이 통화별 상식 범위 안인지, `금액`이 기입돼 있고 부호 규칙(지출 음수·수익 양수)에 맞는지 | 카드사 원본 내역 · 통화별 상식 환율 범위 표 ([verify2.md](../.claude/agents/verify2.md) 판단 기준 3 — 초기값, 운영하며 조정) |
| 부정 사용 검증 | 법인결제 행이 부정 사용 감지 기준에 걸리는지 — 걸려도 단정하지 않고 `확인 요청`으로만 | 감지 기준 ([fraud-rules.md](fraud-rules.md) 확정 — 실행 시점 파일 기준) |
| 통합 | 어떤 구성으로 실어야 읽히는지 (장부 컬럼·리포트 목차) | 아래 "산출물 양식" (확정) |
| 지휘 | 부분 실패 시 파이프라인을 중단할지 남은 단계를 계속 갈지 | 실행 로그·오류 내용 |

## 거래 표 스키마 (확정 v1)

수집이 만들어 통합까지 그대로 흐르는 공통 컬럼. 바꿀 땐 이 표만 고치고 각 단계는 여길 따른다.

| 컬럼 | 설명 | 채우는 단계 |
|---|---|---|
| `transaction_id` | 거래 고유 번호 (`tx_{YYMMDD}_{순번}`) — 행 식별과 검증 결과 대조의 기준 키. 할부는 회차가 지나도 같은 값 유지 | 수집 |
| 날짜 | 결제일 | 수집 |
| 금액 | 부호로 지출/수익 구분 — 지출은 음수, 수익은 양수. 비었거나 숫자로 해석 불가면 오류 (기간·금액 검증 확인) | 수집 |
| 결제처 | 실제 가맹점명 — PG사 표기는 가공이 정규화 | 수집 → 가공 |
| 카테고리 | [categories.md](categories.md) 체계 (확정) — 결제처가 애매하면 구매항목을 참고 | 가공 |
| 비고 | 부가 정보 (원문 표기·메모) | 수집·가공 |
| 결제수단 | 카드·현금 등 | 수집 |
| 결제구분 | `개인결제` / `법인결제` — 결제수단 명의 기준 | 수집 |
| 원거래통화 | 해외결제면 원거래 통화 코드(예: `USD`), 국내 결제는 빈칸 — **해외결제 여부는 이 컬럼이 채워져 있는지로 판별한다** (별도 여부 컬럼 없음) | 수집 |
| 원거래금액 | 해외결제면 원거래 통화 기준 금액, 국내 결제는 빈칸 | 수집 |
| `source_type` | 원천 구분 — `card_excel`(카드사 엑셀)·`receipt`(영수증)·`manual`(직접 입력) | 수집 |
| `collect_status` | 수집 품질 — `확인됨`·`대기`·`확인 필요` | 수집 |
| 구매항목 | 영수증에서 추출한 구매 물품, 콤마로 구분 (마트·편의점처럼 결제처만으론 뭘 샀는지 알기 어려운 경우 가공의 카테고리 판단을 돕는 용도) — 영수증이 없거나 확인 전이면 빈칸. 맨 끝 컬럼 | 수집 |

- 해외결제 환산 검증: 기간·금액 검증이 `|금액| ÷ 원거래금액`으로 유도한 환율이 **통화별 상식 환율 범위 안이면 통과** (범위 표는 [verify2.md](../.claude/agents/verify2.md) 판단 기준 3 — 초기값, 운영하며 조정). 기준 환율 재계산(±1%) 방식은 환율 조회 소스 확정 후 2차 과제 — 카드사 부여 환율(정산일 + 수수료)은 결제일 시장 환율과 1 - 2% 어긋나는 게 정상이라 소스가 있어도 허용 오차 재설계가 필요하다 (2026-08-31 확정 로그)
- 수집 내부 필드였던 `transaction_id`·`source_type`·`collect_status`는 공식 컬럼으로 편입했다 — 가공 이후 단계도 그대로 보존해 흘리고, 검증·통합은 `transaction_id`를 행 대조 키로 쓴다

## 실행 파라미터 (확정)

- **대상 월** (`YYYY-MM`) — 결산 실행 1회의 범위. 지휘가 사용자 요청에서 확정해 **각 단계 호출 시 파라미터로 전달**하고 실행 로그에 기록한다
- 수집은 대상 월 위주로 모으되 걸러내는 책임은 지지 않는다 — 범위 밖 데이터의 반려는 기간·금액 검증이 담당한다 (필터 책임을 한 곳에 유지)
- **부정 사용 감지 토글** (`fraud_check`, 기본 꺼짐) — 웹 업로드 화면의 옵션으로 켠다. 켠 실행에서만 지휘가 부정 사용 검증을 검증 스테이지에 함께 호출하고, 실행 로그에 토글 값을 기록한다. CLI 실행 경로는 실행 인자로 받는다

## 산출물 양식 (확정)

- **엑셀 회계장부**: 거래 표 스키마와 동일 컬럼 (확정) — 계정과목 컬럼은 도입하지 않는다. `카테고리`가 `결제구분`에 맞는 체계([categories.md](categories.md) 개인/법인 표)의 값이면 충분하다
- **PDF 결산 리포트 목차 (확정)**:
	1. 결산 개요 — 대상 월·대상 카드(결제수단×결제구분), 총지출/총수익/순액. 앞 단계 결과가 비어 "미완"인 자리가 있으면 여기에 함께 고지. 리포트 제목에 대상 연월을 표기 (예: "2026년 8월 결산 리포트")
	2. 월별 비교·추이 — 전월 대비 총지출/총수익/순액 증감 표 + 같은 해 보관된 월들의 추이 표·그래프(월 4개 이하는 막대 — 표 두 개를 그래프 오른쪽에 배치, 5개 이상이면 지출·수익 꺾은선). 데이터 원천은 지휘의 월별 보관(`archive/<월>/summary.json`) — 보관 데이터가 없으면 "비교 대상 없음" 표기 (통합이 `archive/`를 읽기 전용으로 접근 — 지휘 담당 승인, 확정)
	3. 종합 분석·인사이트 — 공통 인사이트(전월 대비 총지출 증감·최대 지출 카테고리·최대 단일 지출·확인 필요 건수 등 규칙 기반 요약문) + 개인/법인 구성비(100% 누적 가로 막대) + 결제수단별 합계(가로 막대, 라벨에 금액·비중) + 주요 지출 Top 10 표(지출 행만 대상)
	4. 법인결제 분석·인사이트 — 법인 카테고리 파이(상위 9개 + "기타" 묶음, 범례에 금액·비중) + 법인 인사이트(전체 대비 비중·전월 대비 증감·카테고리 집중도·최고 단일 건·주말 결제·반복 결제처 — 부정 사용 검증 확인 요청 건수는 그 결과가 있는 실행에만)
	5. 개인결제 분석·인사이트 — 개인 카테고리 파이(상위 9개 + "기타" 묶음, 범례에 금액·비중) + 개인 인사이트(전체 대비 비중·전월 대비 증감·최대 카테고리·반복 결제처·최고 단일 건)
	6. 해외결제 명세 — 환산 내역
	7. 확인 필요 항목 — 검증 반려·미완·오류. 컬럼: `transaction_id`·날짜·결제처·유형·사유 (장부 대조 키 포함)
	- 중복 게재 금지 원칙: 같은 수치를 표와 그래프에 두 번 싣지 않는다 — 그래프가 수치 라벨(범례·막대 라벨)로 금액·비중을 보여주면 표는 생략한다 (개인·법인 카테고리 세부는 각 파이 범례가 대신한다. 카테고리 체계는 이원화 — 각자 자기 체계로 집계, [categories.md](categories.md))
	- 구분별(개인/법인) 전월 대비 증감의 데이터 원천은 보관 집계의 `by_payer` (같은 summary.json — 없으면 그 인사이트 줄만 생략)

## 단계 결과 보고

모든 단계는 산출물과 별개로 **같은 형식의 결과 보고**(envelope pattern)를 지휘에게 돌려준다. 지휘는 이 보고만 읽고 다음 호출·중단·오류 처리를 판단하며, 산출물 내용은 열어보지 않는다.

```json
{
  "stage": "collect",
  "status": "ok",
  "output": "collect/result.csv",
  "counts": { "total": 123, "ok": 120, "flagged": 3 },
  "flags": [
    { "row": 12, "type": "확인 필요", "reason": "가맹점 식별 불가" }
  ],
  "message": ""
}
```

- 필드 설명 (1뎁스):
	- `stage` — 보고 주체 (단계 영어명: `collect`·`refine`·`verify1`·`verify2`·`verify3`·`merge`)
	- `status` — 단계 전체 상태 (아래 4개 어휘 중 하나)
	- `output` — 산출물 파일 경로. 산출물 형식은 단계마다 다르며(인터페이스 표 "모양" 열) 이 필드는 경로만 담는다. 여러 개면 배열(예: 통합의 엑셀 + PDF), `empty`·`failed`면 빈 값
	- `counts` — 처리 건수 요약: `total` 입력 전체 · `ok` 정상 · `flagged` 문제 건. **단위는 전 단계 공통 "거래 행"** — 수집은 추출한 행, 검증은 검사한 행, 통합은 장부에 실은 행 (파일·이미지 개수는 `message`에). 단계 간 `total` 대조가 유실 감지의 근거
	- `flags` — 행 단위 문제 목록 (`row` 행 번호 · `type` 문제 유형 · `reason` 사유 한 줄)
	- `message` — 사람이 읽는 자유 메모 (없으면 빈 값). **`failed`일 때는 실패 사유를 반드시 적는다** — 빈 `message`의 `failed`는 규격 위반이며, 지휘는 요약에 "사유 미기재 실패"로 명시한다
- `status` 어휘 (4개 고정):
	- `ok` — 정상 산출
	- `empty` — 처리할 대상 없음 ("수집 대상 없음"·"대상 없음"이 여기 대응)
	- `partial` — 산출했지만 flagged 건 있음 ("확인 필요"·"미완"·반려 건 포함)
	- `failed` — 단계 실패, 산출물 없음 (지휘는 중단·오류 보고)
- `flags[].type` 어휘: `확인 필요`(가공) · `반려`(분류/기간·금액 검증) · `확인 요청`(부정 사용 검증) · `오류`(수집 OCR 실패 등) · `미완`(통합)
- 인터페이스 표의 "못 할 때" 문구는 사람용 표현이고, 이 보고가 그 기계 규격판이다. 보고는 지휘가 실행 로그에 그대로 기록한다.
- **전달 방식 (확정)**: 보고는 단계가 파일로 남기는 것이 아니라 **단계 호출의 응답(반환값)으로 지휘에게 직접 전달**한다. 호출 계층에서 이 규격의 JSON 스키마를 강제하고(구조화 출력), 형식 위반은 호출 실패로 처리한다. 지휘는 받은 보고 원문을 실행 로그 디렉터리에 `report-<단계>.json`으로 아카이브한다 (아래 "실행 로그 형식"). 단계가 보고를 자기 칸에 별도 파일로 남기지 않는다 — 기존 `collect/result-report.json` 방식은 이 확정으로 대체한다 (collect의 화면은 데이터 준비 도구로 두고, 파이프라인의 수집 "실행"은 준비된 데이터를 읽어 보고를 반환하는 호출로 분리).

## 실행 로그 형식

- 실행 1회당 run 디렉터리 하나: `logs/run_YYYYMMDD_HHMMSS/` (쓰는 주체는 지휘 하나)
	- `run.log` — 진행 로그. 줄 형식: `시각 | 단계 | 상태(시작/완료/실패) | 처리 건수 | 메모` — 웹 실행 경로의 중간 확인 시에는 상태 `확인 대기`/`확인 반영` 줄이 추가로 남는다 (아래 "다음 단계" 2026-08-26 중간 확인 확정 로그)
	- `report-<단계>.json` — 각 단계가 반환한 결과 보고 원문 아카이브 (위 "단계 결과 보고" 전달 방식)

## 세는 법 메모

- 산출물 개수가 아니라 **갈라져 나가는 목적지 수**로 단계를 센다. 엑셀 장부 + PDF 리포트는 한 묶음으로 같은 곳에 전달되므로 통합은 한 단계.
- 분류/기간·금액 검증(토글 시 부정 사용 검증 포함)은 같은 입력을 동시에 받는 병렬 구조 — 검증 리포트들은 통합 전에 merge.
- 이후 웹 확장 등으로 산출물이 서로 다른 소비자에게 갈라지면 그때 단계를 쪼개고 분담표를 함께 고친다.
